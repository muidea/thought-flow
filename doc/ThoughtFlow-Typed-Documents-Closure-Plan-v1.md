# ThoughtFlow 类型化文档能力完整收口方案

- 版本：1.0
- 日期：2026-10-21
- 状态：待实施的设计基线，不表示代码已实现或全量测试已通过。
- 代码基线：`muidea/thought-flow@9c859da159eb993ae0bb6fde28a2915182fb3916`；编写前核对远端 HEAD 与此一致。
- 适用对象：设计文档、调研报告、博文；普通碎片笔记保持轻量体验。
- 目标：最终文档结构严谨、内容可核对、前后一致，能够指导实施、决策、复现或传播。

## 1. 收口结论

在现有 DocumentProfile、DocumentDraft、Markdown 渲染、Capture、Compose 和任务体系上增量完善，不另建一套模板系统，也不将项目改造成通用工作流平台。

本次需要收口的是完整的文档交付过程，而不是增加几个生成提示词：

**类型与用途明确 → 输入与来源冻结 → 结构化生成 → 确定性渲染 → 最终正文验证 → 修订及必要确认 → 不可变定稿 → 一致导出与后续使用。**

五条不可破坏的约束：

1. 验证必须绑定实际交付正文，不能沿用生成前、编辑前或其他版本的结果。
2. 模板哈希、原始素材哈希、正文哈希分别建模，不得相互替代。
3. 格式通过不等于事实正确；语义审查和人工确认必须如实标注验证范围。
4. 保存草稿与正式定稿分开：允许不完整草稿，禁止把未满足交付条件的内容标成正式定稿。
5. 新功能不破坏已有 Capture/Compose 幂等、素材版本控制、Git 路径隔离与 Reader 隐私开关。

## 2. 当前实现及真实缺口

### 2.1 应复用的能力

| 当前能力 | 实现位置 | 处理方式 |
|---|---|---|
| 内置设计、调研、博文及普通笔记模板 | `assets/documentformats/*-v1.md` | 复用，新验收规则通过新版 Profile 演进 |
| Profile 解析、版本、内容哈希和注册表 | `internal/pkg/documentprofile/profile.go`、`registry.go` | 复用身份与版本机制 |
| 结构化正文 | `models.DocumentDraft` | 保留，补充事实、约束和可追溯信息 |
| 确定性渲染及基本校验 | `documentprofile/render.go` | 拆分渲染与最终验证，减少正则启发式 |
| 必需章节、单一标题、重复内容、长度、占位符、引用 ID 检查 | `documentprofile/render.go` | 纳入统一规则体系 |
| Capture 上下文、冲突、预览及过期检查 | `capture/biz/scratchpad.go` | 保留，作为统一流程的输入有效性检查 |
| Compose 后台生成、有限修复、草稿保存 | `compose/biz/service.go` | 复用，不新增第二套生成入口 |
| 持久化保存命令及 Thought ID，避免失败重试重复建笔记 | `ComposeDraft.SaveCommand`、`CaptureCommand.ThoughtID` | 必须保持兼容 |
| 素材篮原子移除、版本检查、前端读写协调 | composedraft Store、HTTP、`web/app.js` | 保留并扩充回归测试 |
| Markdown 内容、运行态存储、Git 提交、SSE | 现有模块 | 复用，新增文档事件和明确的提交路径 |

### 2.2 必须补齐的断点

1. **最终正文绕过验证**：Compose.SaveDraft 接受编辑后的 `req.Content`，随后执行 Capture；现有生成期校验不能证明该内容仍合格。普通正文 PATCH 同样需要处理验证失效。
2. **证据没有完整落地**：Thought 保留 Profile 引用，但没有完整的正文版本与验证报告关系。
3. **哈希语义不同**：DocumentProfileRef.ContentHash 标识模板；Capture ContextHash 标识输入上下文；现有 Thought.ContentHash 不是统一定义的最终交付正文凭据。
4. **验证能力有限**：引用 ID 存在不能证明来源可靠或支持结论；重复文本、字数和行覆盖不能证明逻辑一致或可实施。
5. **声明与执行需对齐**：HeadingLevel、RequireNonEmptySections 等配置必须明确执行语义，不能出现声明了但实际未参与校验的状态。
6. **不同入口标准不一**：Capture 与 Compose 的输入、来源及验证条件需要统一，不能依赖某个前端页面自觉调用。
7. **存储文件不等于交付文档**：当前 Thought Markdown 包含 front matter 以及 Original、Extracted Content、AI Notes、Links 等封装；不能把整个内部文件直接当作已验证正文导出。

## 3. 范围与非目标

### 3.1 本次包含

- 三种指定类型的文档契约、必需输入和验收规则。
- 最终正文结构验证、重要一致性检查、可用性检查。
- 正文修订、来源快照、验证报告、定稿及导出绑定。
- 人工编辑、自动修复、来源变化、模板变化后的验证状态管理。
- Capture、Compose、普通编辑、后台处理及导出路径的一致性。
- 历史文档兼容、分阶段迁移、故障恢复与验收测试。

### 3.2 本次不包含

- 保证所有事实正确，或以模型评分代替专业判断。
- 任意代码、文档中的命令自动执行；技术示例默认仅检查，不执行。
- 任意 URL 自动访问以“验证引用”；网络验证必须受现有隐私策略及访问限制控制。
- 多进程同时写同一工作区、多人实时协同编辑、分布式事务。
- 自动发布到博客平台、自动部署设计、自动执行调研建议。
- Word/PDF 全格式生产。第一阶段以 Markdown 为规范交付格式，未来格式转换不能反向改变规范正文。

## 4. 文档契约设计

### 4.1 概念

DocumentProfile 继续负责类型、模板和基础规则；新增的 DocumentContract 是**某次文档任务的具体交付要求**，不是替代 Profile 的另一套模板。

契约至少包含：

- Profile 精确引用：ID、版本、模板哈希。
- 用途、读者、交付语言、适用范围及非目标。
- 输入参数、已确认约束、术语表、事实与假设。
- 输出所需内容、类型化验收项、阻塞条件。
- 来源清单及信息截止时间；未具备的信息明确标记。
- 语义审查策略及人工确认要求。

用户明确指定的类型优先于自动匹配；自动匹配只建议，不得在修复过程中擅自切换类型以绕过规则。

### 4.2 Profile 演进规则

- 增加契约规则需发布新版本，不原地更改已发布版本内容。
- 建议三个类型从 v1 升级到 v2；具体版本号由实现时已有版本决定。
- 新任务选定版本后冻结；生成、修复、验证、定稿均使用该版本。
- 热重载不能让进行中的任务自动使用最新模板。
- 保留旧版本或其快照，使历史定稿可重现；仅依靠运行时 Registry 当前内容不够。
- 不认识的强制校验规则或不支持的 Profile schema 应明确报错，不得默默忽略。
- 用户输入缺失与正文缺失分开报告；不能靠正文中随意写一句话替代未确认输入。

## 5. 三种文档的具体完成标准

### 5.1 设计文档

**必需输入**：待解决问题、目标、非目标、目标读者、现有系统或适用场景。关键技术约束缺失时先作为待决项，不编造现有接口。

**建议内容**：背景、目标与范围、现状、约束、术语、方案、数据/接口/流程、失败路径、备选与取舍、风险、测试、实施步骤、适用时的迁移/发布/回滚、待决问题。

**验收链**：目标 ID → 方案或决策 ID → 验收条件/测试 ID。

检查要求：

- 每个阻塞级目标有方案响应和验证方式；非目标不得在实现计划中被隐式承诺。
- 接口字段、状态值、单位、模块名称在全篇一致。
- 状态转换说明入口、退出、失败和恢复，不只描述正常路径。
- 对需要部署或迁移的方案，说明实施前置条件、执行步骤、成功信号和失败处理。
- 示例接口须标记为现有、拟新增或示意，不把拟议方案写成已实现事实。
- 阻塞实施的未决项必须解决或把文档交付级别明确限定为“提案”，不得标成“可直接实施”。

可用性问题示例：“实现者能否据此确定要改什么、如何验收、失败后如何处理？”

### 5.2 调研报告

**必需输入**：研究问题、用途、范围、比较对象/维度（适用时）、信息截止时间。

**建议内容**：摘要、问题与边界、方法、来源、发现、同口径对比、结论与建议、局限、后续验证。

**验收链**：研究问题 ID → 发现/主张 ID → 来源及证据片段 → 结论 → 建议及适用条件。

检查要求：

- 关键事实附来源；重要推断列出前提，不能把推断改写成来源原话。
- 比较对象的版本、时间窗口、计量单位和实验条件可比。
- 重要相反证据或冲突信息被保留和解释，而不是为得到单一结论而删除。
- 来源只证明“有引用”还不够；支持性审查需指向具体证据。
- 无法获取原文时标为未核验，不得声称已核查内容。
- 结论必须回答研究问题，并说明不确定性和适用边界。
- 建议包含下一步应验证什么、通过什么观察判断，而不虚构责任人或日期。

### 5.3 博文

**必需输入**：读者、核心观点、文章用途/子类型；语气和篇幅可选。

**子类型**：观点、教程、案例。子类型是约束分支，不强制用户填写大量表单。

检查要求：

- 标题、开头、论证与结尾围绕同一核心观点。
- 读者需要的知识前提明确，术语首次出现有适当解释。
- 事实、引用、示例真实程度和适用版本明确。
- 教程：环境、输入、步骤、预期输出、验证和常见失败齐全；未执行的示例标明“未运行验证”。
- 案例：区分真实材料、匿名化处理和假设示例；不得生成虚假实践结果。
- 观点：论据与结论相匹配，说明反例/边界；不强塞部署和回滚章节。
- 允许自然叙事，但不得通过隐藏结构要求牺牲可读性。

## 6. 数据模型与状态

以下是新增设计，不是当前代码已经存在的字段或 API。

### 6.1 建议的核心对象

| 对象 | 关键字段 | 职责 |
|---|---|---|
| DocumentContract | schema_version、profile_ref、purpose、audience、parameters、requirements、constraints、review_policy | 本次交付要求 |
| DocumentRevision | document_id、revision_id、parent_revision_id、body_hash、contract_hash、source_manifest_hash、created_at、origin | 不可变正文版本及输入绑定 |
| SourceManifest | snapshot_id、source_id/type、source_version/hash、retrieved_at、locator、verification_status | 来源身份、版本和可追溯关系 |
| ValidationReport | report_id、revision_id、validation_key、validator_version、checks、issues、review_runs、status | 校验结果及范围 |
| FinalizationRecord | revision_id、report_id、validation_key、confirmed_issues、finalized_at、delivery_level | 指定版本的定稿记录 |
| DocumentHead | generation、working_revision_id、finalized_revision_id | 当前工作版本与最近定稿指针 |

Thought 作为现有知识实体继续存在，新增文档关联信息；不把完整来源或报告堆进其 front matter。现有 DocumentDraft 是生成中间结构，DocumentRevision 才是用户编辑和交付的权威正文。

### 6.2 哈希和验证身份

新增 body_hash，禁止复用 Thought.ContentHash 作为未经定义的替代品。

正文采用 UTF-8；规范化仅处理约定的换行形式及文件结尾。禁止全局删除空行、缩进和尾部空格，避免改变代码、列表或 Markdown 硬换行语义。规范化必须有版本和幂等测试。

验证身份至少绑定：

`validation_key = hash(body_hash, contract_hash, profile_hash, source_manifest_hash, validator_version, review_policy_version)`

结构化数据使用固定字段序和稳定序列化，不能依赖 map 遍历顺序。模型、提示词版本、生成与审查尝试另行记录；语义审查不宣称可完全确定性重放。

验证报告保存完成后不得修改为适配另一正文。报告过期的判断来自身份比较，而非依赖客户端传入的 valid 字段。

### 6.3 状态分离

不要用一个 status 同时表示任务完成、文档正确和发布状态：

- 修订生命周期：draft / finalized（某一不可变版本）。
- 验证状态：not_run / running / passed / failed / needs_review / error。
- 报告新鲜度：current / stale / unavailable。
- 交付级别：proposal / ready_for_use，后者仍不代表事实被数学证明。
- 后台任务沿用现有 queued/running/succeeded/failed/canceled。

编辑已定稿文档会创建新草稿版本；历史定稿不被改写。UI 同时显示“当前草稿未验证”和“上次定稿版本”，不得把上次通过状态展示成当前通过。

## 7. 验证引擎

### 7.1 统一职责

建议增加 `documentvalidation` 包，提供与业务入口无关的验证服务。输入是冻结的正文、契约、来源快照和规则版本；输出为完整报告。

- `documentprofile`：模板解析、注册、规则声明、结构化渲染。
- `documentvalidation`：最终正文 AST 检查、确定性规则、语义审查聚合、可用性检查。
- `documentstore`：不可变修订、报告、定稿记录和 HEAD。
- `document` 业务协调服务：任务调度、状态转换、CAS、幂等及事件；不在 Store 中调用模型。

这些是职责边界；是否形成独立注册 Module 以项目现有注入方式为准，但只能有一个文档写入协调入口。

### 7.2 确定性验证

至少包括：

- Profile/schema/参数有效；必填输入已提供或以规则允许的待决状态明确记录。
- 必需章节/语义块存在，标题层级与类型规则一致。
- 必需章节不以“待补充”等占位词伪装完成。
- 单一文档标题，跨章节重复标题规则允许合理作用域，而不是全局禁止所有同名子标题。
- 未展开模板变量、结构化字段遗失、引用 ID 重复或不存在。
- 引用实体必须有合法的来源定位或可解释的不可访问状态；不能只有空 ID。
- 代码围栏和内部链接有效；代码块中的标题/引用文本不当成正文结构。
- 类型化约束、目标与验收项的引用完整性。
- 长度是约束之一，不作为质量评分替代品。

采用 Go Markdown AST 解析组件，需固定版本并确认与前端渲染规则兼容。选型是实现任务；本方案不把尚未验证的具体库当作既定依赖。

### 7.3 一致性及语义审查

确定性可检查的事实优先结构化：术语、接口字段、状态枚举、数值单位、目标/测试 ID。自由文本矛盾交由语义审查辅助识别。

每条语义问题必须包含：问题代码、严重级别、章节/位置、证据片段、依据、建议及是否需人工确认。不给一个总分就宣布可用。

- 引用真实性、可访问性、结论支持性分开记录。
- 区分事实、推断、假设、建议；已有 Assumptions 字段需在合适章节显式呈现，不能静默丢弃。
- 审查失败/超时标为 error 或 needs_review，不得当作 passed。
- 模型生成与审查分成独立调用，审查只输出问题；不能静默改写事实。
- 不要求同一供应商或不同模型才能实现，但应记录审查配置，不把“多模型一致”当事实保证。
- 网络源和模型输出均是数据，不允许其指令改变验证规则、调用权限或自动发布行为。

### 7.4 定稿门槛

共同条件：当前修订/报告身份一致；结构硬错误为零；必需类型验收项完成；必需审查没有 error；阻塞问题已解决；需确认的事项存在针对本修订的明确确认。

确定性硬错误不能点击“忽略全部”通过。语义疑点允许按策略人工复核，但必须记录理由、对象和修订；确认是用户承担判断，不是把未验证事实改成“验证成功”。

无 AI Key 时：普通笔记和类型化草稿均可使用；结构检查仍可运行。允许通过明确的人工审查路径定稿，UI 标为“结构检查通过 / 人工审查”，不可伪装成 AI 语义检查通过。未完成所需人工审查只能保存草稿。

## 8. 权威正文、修订和存储一致性

### 8.1 正文边界

第一阶段以现有类型化 Thought 的 `AINotes` 作为工作正文适配来源，但必须定义唯一的 ExtractDocumentBody 适配器；不在多个入口自行选择 Original/Extracted Content/AI Notes。

正式修订保存独立 `body.md`，它是验证、预览和导出的共同输入。内部 Thought 文件的包装标题、front matter、系统链接及自动摘要不属于这份正文。

要求 `ExtractDocumentBody(ReadThought(WriteThought(body)))` 在支持范围内保持正文语义与规定字节规范一致。当前分节解析使用保留标题匹配，且未识别代码围栏，应将正文或代码块中的同名标题视为必须覆盖的风险。先修复适配或引入明确、版本化的正文编码，再启用严格定稿；不能只读回截断内容后验证它，再宣称原文完整。所有剥离来源附录、换行处理、标题处理均须发生在冻结正文和验证之前。

### 8.2 人工自由编辑与结构化信息

不能承诺任意 Markdown 都能无损反推为原 DocumentDraft。两条路径分别处理：

- 结构化编辑：修改 section、reference、parameters，经过 Render 生成正文并验证。
- 自由 Markdown 编辑：保留用户原文为新 draft，旧 DocumentDraft 与该正文的绑定失效，不允许用旧 sections 证明新正文完整。

内置 v2 Profile 必须有与其正文规则对应的 AST 章节/语义块映射，直接从实际正文检查。自定义模板只有声明可靠解析规则或显式结构边界时才能走相同直接定稿路径；缺乏可靠映射时，提供“重建结构并预览差异”，经用户确认后生成新修订。不得把整篇自由正文塞进一个 section 后将其他必需项自动填充。博文的语义段落不能仅凭标题推断，需要显式块映射或经过用户确认的结构重建。

### 8.3 建议持久化布局

内容工作区：

- `documents/{document_id}/revisions/{revision_id}/body.md`
- 同修订目录中的 `contract.json`、`source-manifest.json`、`profile.snapshot.md`、`manifest.json`
- `documents/{document_id}/reports/{report_id}.json`
- `documents/{document_id}/finalizations/{finalization_id}.json`
- `documents/{document_id}/head.json`

运行目录：验证任务、修复尝试中间产物、临时文件和私有来源摘录。

修订及定稿记录是持久业务数据，不得作为可随意删除的搜索索引。私有证据存储需明确备份策略；原证据丢失时状态为 unavailable，而不是继续宣称可复核。

Git 只提交明确的文档文件 allowlist；原始对话、敏感来源摘录、认证信息、完整模型请求默认不提交。正式分享与导出默认只包含正文及允许公开的引用，不输出内部审查/证据目录。

### 8.4 原子提交与幂等

1. 获取文档级锁，读取 HEAD generation 并验证请求期望版本。
2. 构建新修订文件到同文件系统临时目录，写完并校验哈希。
3. 将完整目录原子 rename 到不可变 revision_id；目录存在时核验内容，不能覆盖。
4. 以临时文件 + 原子 rename 发布新的 HEAD；进程内锁下检查 generation 未变化。HEAD 是可见修订的提交点。
5. 执行必要的文件/目录同步以满足约定的崩溃耐久性；rename 不能单独保证断电持久。
6. Thought 正文/索引作为兼容投影更新；投影失败通过持久待处理记录重试，不回滚已发布不可变修订。
7. 对外读取正式文档从修订读取。若投影与 HEAD 不匹配，不得显示为当前已验证；不可继续基于陈旧投影更新。

崩溃产生的未引用完整修订可保留待清理，但不能作为当前内容。报告先写完再写定稿记录，定稿记录完成后再更新 HEAD；所有记录携带同一 validation_key。

定稿请求使用 operation_id 和期望 generation，重复请求返回同一结果；同 operation_id 不同正文/参数返回冲突。所有外部重试必须先检查是否已经完成。

一致性边界：文档 HEAD 与不可变修订是正式文档的唯一权威，Thought 是兼容投影，不把二者声明为同一个原子事务。对已关联文档的后续写入必须先经协调服务；HEAD 已提交而投影失败时阻止基于旧投影编辑，并先恢复或从权威修订重建。search、expander、topicstore 等直接 WriteThought 路径也必须审计。最低层写入增加纯本地指纹守卫，不能继承与新正文不匹配的验证/定稿标记；底层不调用模型。

应用内锁和 CAS 不等于能够锁住不合作的外部编辑器。第一阶段仅支持单个 ThoughtFlow 写进程；对编辑器或 Git 合并通过读前重检发现已发生变化，并避免已知冲突。若要求跨进程严格防丢写，需另行实现文件协调协议，不能宣称本方案的进程内 mutex 已解决。

现有 Compose SaveCommand 继续冻结“保存为 Thought”的第一次命令；它与文档定稿 operation_id 分工不同。不得在重试时接受不同正文而复用旧验证报告。用户要改内容，应先建立新修订/新操作，而不是修改进行中的幂等命令。

## 9. 全入口接入清单

| 入口 | 改造要求 |
|---|---|
| Capture 预览 | 保留上下文检查；产生候选正文修订及报告，绑定 ContextHash 和 validation_key |
| Capture 归档 create/update/supplement | 校验目标版本；以合并后的完整正文为候选，不只校验补充片段；既有严格归档语义不得静默降级 |
| Compose 生成 | 输出 Draft 后渲染，保存候选修订；生成成功不自动等于定稿 |
| Compose SaveDraft | 用户编辑正文必须新建/识别对应修订；验证当前内容；继续支持幂等保存到 Thought |
| 普通 Thought PATCH | 类型化正文修改产生新草稿版本，旧报告不再对当前内容有效；普通笔记保持原流程 |
| ApplyDraftInternal | 同样经过修订协调，不能成为“内部调用免校验/免失效”的旁路 |
| Refiner/Expander | 当前 Refiner 通常更新摘要、标签、标题及 URL 提取内容，不应笼统认定其覆盖 AINotes。摘要、标签等派生元数据可更新；不得直接改写已定稿正文。正文建议进入新草稿/变更提议 |
| Topic 合稿/缝合 | 若修改类型化正文，走统一修订入口；专题自身文档不自动套用其他文档 Profile |
| 外部编辑 Markdown | 通过读取时哈希校验兜底，文件监听只加速。发现差异导入为草稿，不信任手工 valid 标签 |
| 正式导出 | 按明确的定稿 revision_id 读取 body.md，校验绑定；不得重新生成或拼接正文 |
| 现有公开分享 | 保留显式公开开关；新“正式文档链接”只能引用指定定稿。旧笔记分享不自动获得已验证标记 |

工作草稿可保存但必须明确标注。现有 Capture 归档依赖有效预览的接口仍保持严格行为；需要保存未通过候选时使用草稿能力，而不是悄悄放宽旧接口。

## 10. 验证、修复及定稿执行流程

### 10.1 验证

- 在短锁内冻结修订/契约/来源；长时间模型审查在锁外运行。
- 结果写回时重新检查 HEAD 和 validation_key；旧任务结果可留在历史，不得覆盖新版本状态。
- 同一 validation_key 的确定性检查可缓存；语义审查重试有独立 attempt，不将多次不同意见静默覆盖。
- 每个文档限制并发；复用 jobstore/SSE，任务有超时、取消、重试和进程重启恢复策略。

### 10.2 修复

- 只修复选定问题和允许变更的章节；保留修改前后差异。
- 自动修复预算显式配置，建议初值 2 次；达到上限转人工处理，不无限重试。
- 修复结果始终是新修订，并重新执行完整相关校验。
- 不允许为通过校验删除用户目标、删除反面证据、伪造引用、把未知事实改成确定事实。
- 无法机械修复的问题提出具体问题，保留原文，不制造“看似完整”的空话。

### 10.3 定稿

- 服务端读取指定修订及有效报告，不接收客户端自报 passed。
- 核对契约、验证规则、人工确认范围及阻塞项。
- CAS 发布定稿指针；并发编辑返回冲突，用户选择对新版本验证或保留历史定稿。
- 正式导出按记录读取字节；如果对标题、引用、代码格式再加工，必须生成新的交付版本重新验证。
- 历史定稿仍可按原规则导出，必须显示其版本与时间；新模板/新来源不会改写历史真实性。

## 11. 来源、变更与新鲜度

- 内部 Thought/Topic/Compose/Scratchpad 来源必须记录稳定 ID、版本或内容哈希；只存 URL/标题不够。
- 外部来源记录访问时间、定位信息及可保留的证据摘要。无法访问时明确记录，不把链接存在当验证成功。
- 来源快照是此次文档依据。原文后来更新不修改快照；显示“来源有新版本”，由用户决定刷新后新建修订。
- 对当前草稿替换来源清单、契约或模板后，旧 validation_key 失效。
- 模板新版本发布不使历史定稿变成“从未通过”；只对迁移后的新修订重新验证。
- 私有来源不因修复或校验被自动传给新供应商。沿用现有 LLM/Reader 配置与隐私边界，新增传输应明确可见。

## 12. 拟新增 API 与事件

以下为建议接口，不表示当前已实现。命名可以随现有路由规范调整，行为不可弱化。

- `GET /api/documents/{id}`：工作版本、最近定稿、报告新鲜度和修订 generation。
- `POST /api/documents/{id}/revisions`：基于期望版本保存新草稿。
- `POST /api/documents/{id}/validate`：对指定 revision_id 启动校验任务。
- `GET /api/documents/{id}/validation-reports/{report_id}`：结构化检查与证据定位。
- `POST /api/documents/{id}/repair`：基于指定修订/报告生成修复候选。
- `POST /api/documents/{id}/finalize`：指定修订、报告、operation_id 及必要确认。
- `GET /api/documents/{id}/revisions/{revision_id}/export`：显式 mode=draft/final；final 需匹配定稿记录。

写操作使用 If-Match/期望 generation；不要把素材篮 version 与文档 generation 混用。

建议错误：400 参数错误；404 对象不存在；409 版本/幂等冲突；422 明确规则不满足；428 缺少版本前提；503 必需验证服务不可用。异步模型失败在 job/report 中表达，不能返回合格文档。

复用 `job.updated`，补充 document.revision_created、validation_completed、finalized 等事件。事件包含 document_id、revision_id、generation、report_id，不默认广播正文或私有证据。客户端只应用匹配版本事件，断线后以 GET 为准。

## 13. UI 和使用方式

### 13.1 创建

选择“设计 / 调研 / 博文”，明确用途和读者；显示最低必要输入。自动识别只提供默认建议，用户可修改。

### 13.2 编辑与检查

主区域显示正文，侧栏显示结构、证据、一致性、可使用性四组问题。每条问题可跳转原文；过期报告明显标记，不继续显示绿色通过。

编辑期间可保存草稿；“检查”与“定稿”是独立动作。发现关键信息缺失，显示精确问题而不是要求用户重新写整个需求。

### 13.3 定稿与使用

展示具体 revision、检查范围、未验证项、必要人工确认和交付级别。正式下载只输出正文及公开引用，可另选下载验收清单，不混入内部对话/系统审查提示。

设计文档可查看目标与测试对应；调研可查看结论与证据；教程博文可查看步骤、预期结果和未运行项。这些是正文的辅助索引，不另造一份与正文可能矛盾的“结论副本”。

## 14. 配置与安全约束

建议新增配置项（实现前统一命名）：

- 文档能力开关与按类型启用范围。
- 最大正文、来源数量、报告大小、修复次数和任务并发。
- 语义审查启用、模型、超时、预算、人工替代策略。
- 文档记录保留与备份、私有证据保留策略。
- 正式导出策略；不得通过关闭功能开关使草稿自动变为正式文档。

安全底线：

- Profile 为声明式数据，不允许任意执行代码/模板函数。
- 示例命令和代码不默认执行；后续若加入执行验证，需隔离环境、资源限制与明确授权。
- 路径继续执行工作区限制及符号链接防护；文件 ID 不能变成任意路径。
- 对来源抓取限制协议、目标、重定向、大小、超时；Reader 禁用必须保持零第三方 fallback。
- 对日志、错误与报告脱敏，不保存 API Key、认证头或带凭据的 URL。
- 现有公开分享授权不因新增文档版本而扩大；新定稿不自动替换已分享对象或自动发布。

## 15. 迁移与兼容

1. 普通笔记不自动转换，不强制套模板。
2. 老类型化文档保留正文与 Profile 引用，初始化为未验证；禁止批量标为 passed。
3. 初次编辑/验证时懒创建文档关联与修订，迁移应幂等，可恢复，生成前后正文差异可核对。
4. 不对旧文档自动重新调用模型、不自动润色或改写，不因新必填规则阻止读取。
5. 老 Profile 缺失时可读取和导出明确标注的历史内容；不能在缺少模板证据时伪造正式验证。
6. 旧草稿中的 SaveCommand 及既有幂等关系保持不变。新增校验不应重放已完成 Capture。
7. 搜索索引只索引选定的当前正文，不把历史所有版本重复当笔记；索引故障不改变文档定稿真实性。
8. 灰度期按类型启用；关闭新入口后保留已生成数据。若旧二进制不理解新格式，不能直接继续写入，应进入只读或使用经过验证的回滚版本。

## 16. 实施拆分

### M0：冻结契约与基线

- 明确正文边界、状态词义、三类型验收清单与兼容行为。
- 确认所有正文写入点及公开/导出路径。
- 建立正常、格式错误、矛盾、缺来源、过期编辑、异常恢复样本集。

完成条件：开发、测试对“草稿、通过、定稿、可使用”定义一致，方案不依赖隐含约定。

### M1：最终正文验证闭环

- 实现修订、正文哈希、报告、统一确定性校验和定稿 CAS。
- 接入 Capture、Compose、PATCH、内部写入、外部编辑发现及导出。
- 完成基础 UI，正文变化后旧报告立即失效。
- 在启用定稿前完成 Markdown 编解码和 round-trip 稳定性；所有底层 WriteThought 调用纳入守卫审计。
- 首批仅启用设计文档完整链路，其他类型保留现有草稿能力。

完成条件：不存在编辑后复用旧 passed、导出未验证内容或内部入口绕过的路径。

### M2：设计文档可用性

- 加入目标/方案/测试引用、术语和约束记录。
- 加入语义审查、问题定位、有限修复和人工确认。
- 覆盖实施、失败处理及适用时的迁移/回滚。

完成条件：样本文档能据此执行明确的实施/验收，不以必需章节非空冒充可实施。

### M3：调研与博文

- 调研补证据支持链、口径和局限；博文按子类型验收。
- 增加三类端到端样本，保证正文、辅助索引与导出一致。

完成条件：三种类型均走同一最终验证流程，不各自绕开规则。

### M4：迁移、故障和发布验收

- 完成旧资料兼容、崩溃恢复、取消退出、性能预算与隐私测试。
- 按仓库 Makefile/CI 实际可用目标执行测试；不要照搬已过期 README 命令。
- 执行完整 CI、浏览器和 API/SSE e2e，验证单工作区单写进程限制。

完成条件：所有阻塞验收项通过，已知限制写入使用文档；这时才能宣称本功能收口。

## 17. 必须通过的验收用例

| 编号 | 场景 | 预期 |
|---|---|---|
| A01 | 三种文档正常生成、编辑、验证、定稿、导出 | 同一验证身份，交付正文一致 |
| A02 | 删除必需章节或只填占位词 | 草稿可保留，正式定稿失败 |
| A03 | 插入未定义引用/重复引用 ID/空来源 | 明确定位，不假通过 |
| A04 | 正文代码块包含 Markdown 标题或引用样例 | 不被错误计入正文结构 |
| A05 | 编辑后点击定稿，仍提交旧 report_id | 409/422 明确拒绝，不能复用旧结果 |
| A06 | 校验运行中再次编辑 | 旧结果仅属于旧版本，不覆盖新状态 |
| A07 | Profile 热更新或来源替换 | 当前任务仍用冻结输入；显式迁移生成新验证身份 |

| A11 | 修订目录写完但 HEAD 未写时崩溃 | 重启不暴露半完成修订，恢复可解释 |
| A12 | 定稿成功后 Thought 投影失败 | 正式版本完整可读，投影可幂等恢复，不能错误显示当前状态 |
| A13 | 外部修改 Markdown 或手工写 valid 标记 | 当前版本需重新验证，不信任标记 |

| A19 | 素材刷新、添加、清空、保存响应交错 | 保持既有版本/修订保护，不丢素材 |
| A20 | 历史类型化文档与普通笔记升级 | 可读、可恢复，不擅自改写或批量验证通过 |
| A21 | 导出/公开访问当前草稿与历史定稿 | 明确版本和模式，不把草稿伪装成正式版本 |
| A22 | 标题/术语含正文分节保留词 | 保存读取往返不截断正文 |
| A23 | 来源原文后续变化或不可访问 | 历史依据不被改写，当前新鲜度/可核验性如实显示 |
| A24 | 审查或生成任务取消、进程退出重启 | 不写回错误版本，不重复收费调用已完成步骤，任务状态可恢复 |

补充验收：只修改索引状态或非文档标签不应误判正文过期；修改参与校验的标题、参数、引用、Profile 则必须使验证身份变化。规则版本升级需要对当前草稿重新验证，但历史定稿仍标注原规则结果，不追溯伪造新版本检查记录。

结构规则使用可断言 fixture；语义审查用冻结的人工标注样本评估漏报和误报，不以一次模型输出充当回归基准。上线前根据真实样本确定可接受阈值，不在没有数据时杜撰准确率。

## 18. 完成定义及发布门槛

只有同时满足下列条件，才可标记“类型化文档能力已收口”：

- 三类型具备明确且已执行的规则，不存在只声明不检查的关键配置。
- 最终正文、契约、来源、报告及定稿身份完整绑定。
- 草稿、验证、定稿、历史版本在 API 与 UI 中语义一致。
- 所有正文写入口均创建修订或使报告失效，无内部旁路。
- 硬错误不能绕过；语义不确定性和人工判断明确留痕。
- 导出与验证正文一致，内部存储封装不会污染交付内容。
- 迁移不丢正文、不重放 Capture、不扩大分享权限。
- 并发、崩溃、任务取消及隐私相关阻塞用例通过。
- 完整测试结果及未覆盖项被记录，不能用前端单测替代后端和端到端验证。

## 19. 风险与控制

- **过度结构化损害写作**：结构化关键事实与关系，不把全部叙事拆成难用表单。
- **门槛过重**：普通笔记不受影响；草稿随时保存；严格门槛仅用于明确的定稿操作。
- **模型审查自信但错误**：保留证据与不确定性；关键结论需要可核对来源或人工确认。
- **重复维护正文和结构**：明确最终正文权威；人工编辑后旧结构化 Draft 仅作历史，不重新渲染覆盖编辑。
- **多文件持久化半成功**：不可变文件加单一 HEAD 提交点，配合修复任务和读取校验。
- **后台任务破坏成稿**：派生元数据与正文分离；后台只能提交正文变更建议。
- **范围失控**：优先完成设计文档垂直链路，不先引入复杂智能体编排、自动执行或发布平台。
