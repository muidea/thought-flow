# Capture 对话归档收口方案 v1

日期：2026-10-23。状态：C01–C08 已在当前工作树实施；验收与边界见 [实施记录](ThoughtFlow-Capture-Archive-Closure-Implementation-2026-10-23.md)。本文保留修复前的核对证据，不能作为最终提交及双平台 CI 已通过的证明。

2026-10-24 范围修订：用户明确要求自动匹配文档类型、自动填充上下文字段并生成 Thought，避免逐项确认；Capture 页面只保留对话气泡与输入，不展示上下文或归档预览，相关状态由后端管理。本轮取消“提取值必须人工确认”及“无来源不能落盘”的 Capture 门禁，改为保留推断来源、披露编写假设和未核验状态；正文结构、安全性、真实核心缺项与矛盾检查继续执行。正式定稿及公开交付仍按原证据规则检查。下文旧确认要求作为历史方案保留，以 [当前设计修订](thoughtflow-capture-document-profile-design.md) 和 [后续实施说明](ThoughtFlow-Capture-Archive-Followup-2026-10-24.md) 为准。

## 1. 结论与核对范围

当前 ISA-95 会话已经完成 JSON 解析、上下文生成和候选文档持久化，未生成 Thought 的直接原因是归档预览校验失败。继续调整 `response_format` 不能解决这次业务校验失败。

需要分别解决输入契约、问题解除、生成校验、保存可靠性及界面反馈。禁止用自动改成普通 note、伪造引用、填充无意义参数、清空全部冲突或放宽严格归档接口来换取“成功”。未完成内容应提供明确的草稿保存能力。

核对基线：HEAD `f64c68728f9dbc5e9793b5b10265f8c09a456696` 加当前未提交工作树。工作树已有回答字段、JSON 容错配置、Provider 错误处理和相关测试修改；结论不能仅归属到该 HEAD。历史数据兼容按用户此前指示不作为本阶段要求，当前用户会话仍须保护。

本轮读取本地服务会话及落盘数据，核对 Capture、AI、Profile、Scratchpad、documentflow、HTTP 与前端调用链；另外在独立临时目录执行故障与交错测试。没有修改当前用户会话，没有请求新的模型生成，没有执行真实归档、迁移、删除或服务重启。

C01 的互斥锁只保证单次文件写入完整，不能保护跨模型调用的读改写。保存后再检查 ContextHash 也不能补救已被覆盖的新消息：旧消息与旧 hash 可能一起被恢复。

C02 的并发进入测试使用替代 Capture 写入器，不能算并发落盘的完整证明；另一个失败重试测试使用真实 Capture，确实生成不同 ID 的两份 Markdown。两类证据分别记录。

C08 需要准确限定：当前“有预览就不自动再次生成”没有区分有效、无效、过期及未完成提交；但新用户消息通常会清除旧预览，因此不是会话永久不可重试。这里需要恢复与反馈机制，不能仅删除防重复判断导致模型调用循环。

## 4. 必须保留的语义

1. 对话回答、候选材料、已保存草稿、已归档 Thought、已定稿版本是不同状态。
2. “已保存草稿”只在真实 Thought 投影已落盘并可恢复后显示；“已归档”只在严格归档命令成功后显示；“已定稿”继续由定稿报告及记录证明。
3. Capture 现有严格归档门禁保留。原类型化文档方案 §9 已明确：未通过候选使用草稿能力，不能悄悄放宽旧归档接口。
4. 不能确认的受众、标准版本和信息截止时间不得由服务端冒充用户决定；无比较时可由用户明确填写“不适用”，不自动用占位文本消除必填。
5. 来源未核验应保持未核验；能否以提案级交付由现有文档策略决定，保存草稿不赋予公开、正式导出或定稿权限。
6. 原生 `json_object` 只提供 JSON 语法保证，业务 schema 和内容真实性仍需校验。按 2026-10-24 最新要求，JSON fallback 内置自动启用，不使用配置开关；仅在明确且只不支持 response_format 时移除参数并记忆。生成通道关闭 SDK 自动重试，一般网络、429/5xx 和结果未知不自动重发；参数、鉴权或内容校验失败终止，Retryable 与自动重发权限分离，操作共享截止时间。

## 5. 实施设计

### 5.1 会话原子更新与输入代次（先修 C01）

Store 增加原子 Update/CAS，统一替代消息、参数、上下文、策略、预览、提交标记与重置等业务路径中的 Get→Save。禁止只修预览 handler 而保留其他整份覆盖入口。持久化至少区分：

- `session_generation`：每次持久化状态变化递增，用于客户端 If-Match。
- `input_generation`：正文、消息、参数、Profile、策略、目标或冲突决议变化时递增，用于冻结生成输入。

模型网络调用在锁外进行。开始时固定输入代次与 Profile 快照 hash；结束时短事务检查代次、操作身份与上下文 hash，仅写本操作的预览/上下文字段。过期返回 409，保留所有新消息，禁止旧结果更新当前候选 HEAD。文档存储也须按同一 operation/input 绑定发布，不能只阻止 Scratchpad 回写。

用户输入在归档期间仍可保存。归档消费已冻结的代次，完成后的清理不能 Reset 掉更晚输入；后续输入保留为下一轮材料。参数修改、同会话多标签操作以及删除/取消会话，都必须参与相同的代次控制。

### 5.2 首次保存的持久化幂等与故障恢复（C02）

引入会话共享的保存锁与持久化 SaveCommand：包含 operation_id、目标 Thought ID、策略、目标 generation、冻结正文/契约/来源及其 hash。先登记命令，再写 Thought，最后登记结果。客户端重复点击、超时补发、重启重放都复用命令和 ID。

不能只复制 Compose 的调用方式：当前 `Capture()` 仅允许 Compose 使用预留 ID。需要增加受信的 Capture 保存命令入口，校验 operation 与目标归属，避免开放任意指定 ID 后直接复用其他用户内容。已有目标必须核验归属与冻结内容；发现用户后续编辑时保留编辑并返回可解释状态，不覆写。

new/update/supplement 均需要幂等定义；更新使用预览绑定的 generation；补充的父子关系登记可恢复且不重复。标记或投影失败显示“待恢复”，不能显示成功或重试创建新对象。事件和 Git 请求以同一操作身份去重，失败可重放。

### 5.3 Profile 输入契约与确定性预检（C03/C04）

采用受限目录携带真实输入契约的方式：扩展 descriptor，提供 inputs 的 key、标签、required/default、规则摘要与契约 hash，同一上下文请求完成分类及参数提取，控制候选数和总字节数。选定 Profile 后由后端解析并冻结完整快照，后续生成使用该快照的生成约束及证据要求。同一轮新选模板必须拿到它的输入契约，不能只提供上一轮模板；请求返回后若模板 hash 已变化，旧结果不能按新契约直接发布。

参数状态包含 value、来源（用户明确/对话提取/模板默认/模型建议）、对应消息和确认状态。模型建议不能覆盖用户已确认值。仅接受当前 Profile 已声明的业务键；内部参数单独管理。换模板时按新 schema 重新检查，旧键不得无声沿用到新契约。

后端计算 `missing_inputs`，返回稳定 key、中文标签和原因。readiness 由实际输入、证据要求及未解决业务阻塞派生，模型提供建议但不是最终权威。预检在昂贵正文生成之前进行：缺必填输入时直接返回 needs_input 和补充入口，不反复生成注定失败的完整报告。

提供按字段修改、明确清空及确认的 CAS API 和表单，不再要求用户操作整份 SessionContext JSON。已有对话能提取的信息先给出可核对的值；用途、截止时间等仍不明确时集中询问，不要求重复粘贴整段对话。

### 5.4 可解除的问题模型（C05）

将字符串 conflicts 拆成有 ID 的事项：kind、status、blocking、来源消息、所涉字段、说明和 resolution。至少区分业务矛盾、知识局限/待验证、运行诊断。

- 真实业务矛盾保留至用户确认或提供可追溯的新证据解除；模型漏报不能自动消除。
- 知识不确定性写入局限或证据待办；是否阻塞由具体 Profile/交付级别决定。
- Provider 参数、网络、鉴权故障保留在运行诊断，不计入 ISA-95 等主题本身的事实冲突。

修改现有“保留 old conflict”的测试，扩展为“未解决事项不会丢失、已明确解除事项不会再次阻塞”。禁止简单改为全量覆盖或提交前清空数组。

### 5.5 生成与最终校验共用一套约束（C06）

先做输入/来源预检，再生成、渲染、执行最终 Markdown AST 确定性校验。仅将可修复的正文结构问题送入有界 repair，例如缺章节、Q/F/C 关系或已有来源未引用。修复后重新验证实际交付正文，不能只验证中间 DocumentDraft。

缺真实来源、缺用户确认和跨版本冲突返回对应操作，不要求模型编造资料解决。将最终 AST 问题与 renderer 问题统一编码并回送，保留每次尝试与终止原因。空壳本地生成只能作为明确标识的草稿材料，不能以“结构补全”替代证据与真实内容。

预览到 Thought 的冻结传递须包括正文、解析后的参数、Profile 快照、SourceManifest 和证据绑定。目前 `BuildCaptureCommand()` 没有传递 preview.Document 的完整来源清单，且参数取自 SessionContext；实施时验证实际保存契约与已校验契约一致，不允许只比较正文。

### 5.6 明确的“保存草稿”入口（C07）

增加显式 Capture 草稿发布操作，复用 5.2 的保存事务。未通过内容规范的候选可以保存为可编辑 Thought 草稿，仍须通过身份、权限、路径、来源隐私和链接安全检查。正文保留缺项、未核验说明与失败报告，禁止标记 finalized。

不能假设已有候选可直接 POST 普通 `/revisions`：当前 ensureDocument 的例外只覆盖部分 HEAD-only 读取/检查接口。需要实现候选到真实 Thought 的协调发布，并保持不可变版本、资源和删除状态。

确定单一权威对象身份，避免 `capture-<session>` 候选与时间型 Thought 各有独立版本链。建议在首次物化操作预留真实 Thought ID，后续候选与投影统一使用；当前已保留的会话候选按受控恢复路径处理，不删除原对话，也不直接把任意 reserved 对象当作成功保存。

单独返回 `draft_thought_id` 与草稿状态，不提前设置严格归档的 committed 标记；后续补齐后归档应沿用同一物化对象，不能再生成第二份。草稿保存后不清掉对话、不触发通用 refiner 覆写已冻结的类型化正文；草稿后续编辑同样使用 generation。

### 5.7 用户反馈与持久操作状态（C08）

界面至少明确显示：整理中、待补输入、校验未通过、可归档、保存中、已保存草稿、已归档、保存失败/待恢复。问题摘要与操作按钮放正文之前；不直接把英文内部错误文本作为唯一说明。

预览生成改为显式 POST 命令；GET 只读取状态与结果。返回 operation_id、输入代次、状态、是否已持久化和分组问题。预览尚未可靠保存时不能继续提交；只有 `validation.status === valid` 才启用严格提交。

操作状态保存在服务端。SSE 与轮询只刷新视图，浏览器关闭或漏事件不能让已接受的归档永久卡在 preview→commit 间。自动执行必须绑定用户已表达的归档意图及冻结输入；输入变化后暂停旧命令并提示重新预览，不能替用户确认新内容。

恢复页面时查询操作结果，遇 blocked 显示补齐入口，遇可恢复保存失败复用同一命令；禁止仅因 SSE/刷新重复到达就重跑模型。现有 selection epoch 保留，另按 operation/input 校验迟到响应。API 保留结构化错误详情并做中英文映射。

## 8. 本轮验证证据

本轮使用 Go 1.24.13，在临时目录实际执行四个专项探针：

1. `TestAuditReproducesPreviewOverwritingNewMessage`：真实 handler/Store，已追加的新消息被旧预览写回覆盖，重新加载 Store 后仍只有旧消息。
2. `TestAuditReproducesConcurrentFirstArchive`：两个通过有效预览检查的请求同时进入替代 Capture，确认缺少保存串行化。
3. `TestAuditReproducesConflictsWithoutResolution`：后续无冲突结果无法解除旧字符串事项。
4. `TestAuditReproducesDuplicateMarkdownOnCommitMarkerRetry`：真实 Capture 写入后注入提交标记失败；重试生成两个不同 ID，磁盘枚举确认为两份 Thought。

## 9. 当前会话的处理建议

保留现有 Scratchpad、候选正文和失败报告。优先按 A/B 批次修复可靠性与参数契约，再提供显式草稿发布；不要在本轮核对时强制调用 Commit 或手工创建伪成功标记。

若用户只想先保存已经讨论的内容，选择“保存草稿”，清楚保留未核验说明。若需要符合 research-report v2 的严格归档，则补充/确认研究问题、用途、范围、比较关系、截止时间、受众及可追溯来源，解除真实业务矛盾，再进行预览和提交。没有联网检索或标准原文时，应说明资料缺口，不承诺仅切换模型就能补齐。
