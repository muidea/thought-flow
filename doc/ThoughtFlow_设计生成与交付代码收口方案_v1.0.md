## 1 结论与使用方式

本分册只收口 ThoughtFlow 的设计生产端：沿现有 DocumentSet 主链路，把需求和设计决定转为内容完整、定义明确、可追踪、可检查的冻结设计成果集，并为 Workorch 提供不丢约束的有界交接材料。不重构整个产品，也不将问题简化为模板或提示词优化。设计应能支持后续持续开发、验证和 artifact 交付，但生成设计不等于已经实施、批准执行或交付最终产物。

本分册可独立用于 ThoughtFlow 实施：TF-01～TF-12 的编号和实质范围保持不变；共同边界集中在第 16 节 HC-1。Workorch 内部如何调度、恢复、审批、形成证据及验收实际产物，不作为 ThoughtFlow 的实现任务。第 24 节分别定义生产端本地完成、跨项目交接验证和最终 artifact 证据，防止把 Workorch 全部运行时收口当成 ThoughtFlow 本地完成的前置条件。

实施的中心是同一份权威设计合同：Profile 确定必答内容，SharedDesign 保存规范事实，文档引用并解释事实，独立规则与语义审查检查事实和正文，冻结版本绑定审查与导出，Workorch 适配只做有界交接。不得让这些环节各自维护一套含义相似但可能分叉的要求。

跨模型一致性指不同模型遵守相同约束、实现相同可观察行为、满足相同验收标准，不要求文字、代码结构或内部算法相同。文档不能单独保证所有模型持续可靠；符合性必须通过固定合同、恢复上下文、独立验证与真实评估建立。

建议按以下顺序使用本文：

1. 先批准第 4 节不变量与第 20 节启动决策，解决版本和授权边界。
2. 对第 7～11 节模型、关系、验收及 artifact 合同做设计评审，完成 TF-01～TF-05。
3. 按第 19 节工作包实施；测试样例从第一阶段同步建立。
4. 用第 21 节验收矩阵检查每个工作包，不以代码合并代替验收。
5. 在单独获准的模型/预算范围内按第 22 节执行真实评估；按第 24 节分别声明 ThoughtFlow 本地完成与 HC 联合验证状态，不笼统宣称端到端成功。

本文中的“必须”“不得”是拟实施方案的约束；它们不表示对应能力已经存在。所有拟新增类型、字段、文件和接口都需在实现时落实并由测试证明。

### 2.3 授权范围

本分册源于将 ThoughtFlow 与 Workorch 收口内容拆分的要求；当前用户授权为根据评审完善本设计文档。拆分及本轮文档修订均不构成以下行为的授权：

- 修改 thought-flow 或 Workorch 项目代码、提交或合并变更。
- 运行会调用收费模型、部署服务、修改数据库或产生外部副作用的任务。
- 创建 Workorch 正式 DoD、批准记录、Run，或代表用户授予执行权限。
- 自动迁移、重写、清理历史计划、定稿、审查记录或备份。

后续实施可依据本文拆分任务，但仍需遵守实际环境和动作对应的权限要求。设计定稿、设计交接、Workorch 审批和执行授权是不同动作，不得互相替代。

### 2.4 已确认的历史数据兼容豁免

用户此前已明确：“当前阶段不用考虑历史数据兼容性”。本轮沿用该范围决定，不重新要求旧布局、旧 schema、旧 ValidatorVersion、旧客户端或旧格式备份向后兼容，不默认实施历史迁移、批量重算或旧版只读适配，也不将其作为当前阶段的完成前置条件。

豁免不等于可以删除已有数据、忽略 hash、静默升级旧定稿或冒称旧数据已恢复。不支持的记录须保留原字节并给出明确的版本错误；数据迁移或清理不在本次文档修订授权内。新格式在其声明支持的版本内产生的修订历史、跨修订引用、定稿、重启恢复及备份闭包仍属于本轮必需能力。第 9.4 节所称历史事实是这类新格式内部历史，不借兼容豁免删除。

## 3 职责与本轮范围

### 3.1 三层合同

```text
thought-flow                         Workorch                         实施环境
┌──────────────────────┐            ┌──────────────────────┐        ┌──────────────────┐
│ 设计事实与适用范围     │            │ 执行上下文与任务状态   │        │ 代码 构建 测试     │
│ 可读设计与覆盖关系     │ ─有界交接─> │ 正式审批与权限         │ ─执行─> │ 产物 环境 日志     │
│ 预期验收与证据要求     │            │ 调度 恢复 证据判断     │ <─证据─ │ 实际可观察结果     │
│ 冻结基线与公开设计包   │            │ 最终 artifact 验收     │        │                  │
└──────────────────────┘            └──────────────────────┘        └──────────────────┘
```

thought-flow 负责定义应当满足什么、为何如此、适用范围、如何验证以及预期证据。Workorch 负责将这些输入转为受约束的执行，管理实际代码、任务、证据和批准。实施环境产生实际执行结果；任何模型的自述都不能替代这些结果。

### 3.2 本轮纳入

- 工程设计成果集 Profile、角色内容要求、适用性与缺口表达。
- SharedDesign 规范语义、来源、确认状态、关系、artifact 及验收要求。
- 工程专用生成、独立质量门禁、修订影响与冻结身份保护。
- 公开设计包、Workorch 专用交接预览及资源预算校验。
- 现有 Web 和 API 的最小可操作闭环。
- 确定性回归、真实跨模型评估规程与消费者验证。

### 3.3 本轮不主动改造

不重写 magicCommon 框架装配、单二进制部署结构、DuckDB 搜索、embedding、URL 抓取、普通专题匹配、Git 同步引擎或通用调度系统。涉及这些能力的必要回归仍需保留；新增设计事实专用搜索不是本轮前置条件。

动态任务分解、持续运行检查点、代码修改、构建部署、真实测试执行、正式权限和最终 artifact 判断属于 Workorch 或实施环境。本方案不在 thought-flow 内复制这些状态机。

### 3.4 独立实施与共同边界

| 对象 | ThoughtFlow 分册负责 | 本地完成不代表什么 |
| --- | --- | --- |
| 规范设计与内容质量 | Profile、SharedDesign、生成、修订、独立门禁、冻结身份 | 设计正确不等于实际实现正确 |
| 公开设计包 | 不可变完整基线、公开清单、离线校验与隐私保护 | 文件可导出不等于消费者环境已安全接收 |
| 有界交接材料 | 来源分层、需求映射、范围闭包、精确预算和预览 | 设计事实 ID 不是消费者正式对象或 owner 身份 |
| HC-1 联合验证 | 生产端输出及自检；配合核对实际消费结果 | 不需要先完成全部 Workorch 运行时任务；未联调不能宣称交接可用 |
| 最终 artifact | 定义预期形态、构建运行与验证合同 | 不在 ThoughtFlow 内执行构建或伪造最终产物成功 |

这里的“实际测试执行”不包括 ThoughtFlow 自身实现所需的获准回归和质量评估。ThoughtFlow 自身测试仍是本分册验收责任；由设计驱动的业务实现、构建、部署及业务产物测试则属于消费者和实施环境。两者的权限与证据必须分开。

## 4 必须保护的核心不变量

| ID | 不变量 | 必须阻断的反例 |
| --- | --- | --- |
| INV-01 | 每项实施目标可追溯到当前范围内要求或获批变更 | 模型因“有帮助”自行新增功能 |
| INV-02 | 同一语义事实只有一个权威定义 | 两篇文档分别维护同一接口字段 |
| INV-03 | 建议、假设、冲突与已确认事实不可混同 | 模型自行将推断标为用户已确认 |
| INV-04 | 完成声明必须绑定相应有效证据 | 未运行测试被写为通过 |
| INV-05 | 审查、文档、公开模型和交接指向同一候选或定稿 | 新正文搭配旧审查、新合同搭配旧 hash |
| INV-06 | 上游变化使受影响派生物与结论失效 | 改验收后仍显示旧版已通过 |
| INV-07 | 冻结历史不可被静默覆盖 | 模板升级直接改写旧定稿 |
| INV-08 | 公开交付不包含私有 Capture、对话原文和内部引用原文 | 直接序列化内部存储对象导出 |
| INV-09 | 有限交接不能通过截断、漏约束或伪造 ID 过预算 | 只保留容易实施的验收 |
| INV-10 | 工程严格规则不污染一般归档与研究模式 | 普通笔记因缺 artifact 合同无法保存 |
| INV-11 | 验收标准独立于实现模型的临时判断 | 为让测试变绿而降低预期结果 |
| INV-12 | 换模型、重启、恢复后仍使用可重建的固定上下文 | 依赖上一轮模型记忆补全合同 |

这些不变量应成为测试名称、错误码和审查清单的共同来源。无法证明不变量成立时，应呈现阻塞、未验证或未完成，而不是自动降级为成功。

## 7 TF 01 必需内容与 Profile

### 7.1 逻辑内容范围

以下内容不强制各占一个物理文件。一个角色可承载多类内容，一类内容也可由多篇文档解释，但权威定义归属必须唯一。

| 内容域 | 必答问题 | 典型权威载体 | 适用性判断 |
| --- | --- | --- | --- |
| 目标与范围 | 谁、问题、成功条件、必须做、不做、范围边界 | 需求与范围事实 | 所有工程成果集必需 |
| 业务行为 | 前置条件、输入、主流程、输出、异常、边界 | 行为和状态规则事实 | 所有功能需求必需 |
| 架构与职责 | 模块、依赖、状态归属、协作、禁止调用 | 模块与决策事实 | 按实际模块复杂度 |
| 接口 | 输入输出、字段、错误、权限、幂等与兼容性 | 接口事实 | 存在模块或外部交互时 |
| 数据 | 字段约束、存储、生命周期、保留与删除 | 数据事实 | 存在持久或共享数据时 |
| 运行与恢复 | 并发、超时、重试、中断、恢复、释放 | 运行规则事实 | 按执行与副作用性质 |
| 质量约束 | 安全、性能、容量、可观测性及测量条件 | 质量约束事实 | 每项说明适用性 |
| 验证与验收 | 方法、预期、边界、负例、证据与判定 | 验收事实 | 每项必需要求都需要 |
| artifact 交付 | 形态、内容、入口、构建、运行、环境、说明 | artifact 事实 | 所有正式交付必需 |
| 变更与限制 | 未决问题、例外、依赖、修订和重新检查 | 问题与修订投影 | 所有正式交付必需 |

每一内容义务的状态只能是：`DEFINED`、`NOT_APPLICABLE`、`UNRESOLVED`。这是拟新增的语义状态，不是当前实现枚举。`NOT_APPLICABLE` 必须包含理由和评审依据；空值、缺字段和模型猜测不能当作不适用。

### 7.2 拟新增 Profile 语义

建议在现有 Profile 和成员角色上表达内容义务、适用条件、必需事实类型、关系要求、禁止替代物及质量策略版本。最终 Go 字段命名在 P0/P1 评审后确定，不应从本文示意直接推定已有字段。

- 内容义务必须具有稳定 ID，例如 `OBL-RUNTIME-RECOVERY`。
- 一个义务引用事实 ID 或正文锚点作为设计落点，并说明承担权威定义还是解释。
- 适用性应由显式事实或已确认判断驱动；未知条件保留为问题，不直接当成 false。
- 条件变化后重新计算所需成员、覆盖和影响；不能继续使用旧的“无需生成”判断。
- Profile 冻结快照保留原内容与版本，新 Profile 仅用于新计划或显式修订。
- 普通笔记、研究和一般单篇文档继续使用原用途规则，不强加工程 artifact 义务。

### 7.3 实施任务与验收

产出：工程 Profile 规范、角色内容表、适用性样例、至少一个完整业务闭环样例。主要代码落点为 `internal/pkg/documentset/profile.go`、`internal/pkg/documentprofile/` 和 `assets/documentformats/design-doc-v2.md`。

验收时分别提供一个标题齐全但内容空泛的反例、一个合理不适用的样例、一个条件未知的样例。前者必须失败，第二个需保留理由，第三个必须显示缺口；不得用标题存在、字数达标或章节被通用文本填充作为完成依据。

## 8 TF 02 与 TF 03 规范事实与确认

### 8.1 扩展现有 SharedDesign 而非复制

规范事实继续进入现有 `SharedDesign.Facts` 及其关系体系。正文、覆盖矩阵、公开包和 Workorch 交接都是投影；它们不再保存一份可独立编辑的同义要求。

当前 `FreezeShared` 对事实类型和条件类型显式白名单校验，基线有 requirement、term、module、interface、entity、decision、constraint、verification 共 8 类事实和 2 类条件。新增事实语义需要同步更新规划提示、模型输出解析、白名单、冻结、验证、渲染、身份与测试，不能只修改 `types.go`。

拟新增的语义类别包括状态规则、可判定验收、质量测量条件、artifact 合同等。推荐默认方案是在现有 Fact 中增加受 kind 约束的类型化 payload，保留现有 ID、Owner、来源和关系作为唯一身份与归属；验收默认复用 verification 并增加 acceptance payload，状态规则和质量要求默认复用 constraint 并使用不同 payload；artifact 规范推荐增加 artifact_spec 种类并同步白名单。其他新语义确实无法由现有 kind 表达时才扩展枚举。不得再建可独立编辑的 requirements/acceptances/artifacts 平行集合。

建议将验收 payload 固定为第 8.4 节示例的前置、操作、观察、判定、方法和证据要求，将质量 payload 固定为第 10.2 节测量合同，将 artifact payload 固定为第 11 节交付维度；状态规则 payload 则明确初始状态、触发、守卫条件、目标状态、失败结果和持久化要求。缺失关键字段即不满足相应合同，不交给生成器自行解释。D-03 只决定这些语义在现有种类中的最终编码，不重新开放是否需要这些内容的讨论。

### 8.2 事实字段职责

| 概念 | 建议表达 | 强制规则 |
| --- | --- | --- |
| 稳定身份 | `id` | 同一语义事实修订保留 ID；跨修订精确引用、拆分合并与退役按第 9.4 节 |
| 语义类型 | `kind` | 受注册表和 schema 校验，不接受任意字符串冒充合同 |
| 权威归属 | `owner` | 精确到稳定成员键；角色不替代成员身份，不能两处同时权威 |
| 规范程度 | `modality` | MUST、MUST_NOT、MAY、NEEDS_CONFIRMATION |
| 知识状态 | 内部 `Fact.Status`，公开 `epistemicStatus` 为派生 | 不建立双写状态，映射见下文 |
| 来源 | `provenanceRefs` | 引用来源记录，不把正文引用当作批准 |
| 内容与结构 | `content` 及类型化 payload | 人类描述与可判定字段不相互矛盾 |
| 范围 | `scopeRefs` | 说明属于哪些已声明范围，不暗中缩减 |
| 变更关联 | 修订记录中的事实引用 | 旧版不改写，新版说明原因及影响 |

上述名称是拟议合同，不代表当前 JSON 或 Go 结构已经具备。应优先复用现有 ID、Owner、Fields、来源和关系机制，只增加无法准确表达的语义。

内部确认状态继续以现有 `Fact.Status` 为唯一事实源，其当前值为 confirmed、proposed、unresolved；不再增加一份可独立写入的 epistemicStatus。推荐将假设/冲突作为 unresolved 事实关联问题的类型，公开投影派生为 assumed/conflicted；普通 unresolved 保持 unresolved，confirmed/proposed 则一一映射。若同一事实同时有关联假设和冲突，展示 conflicted 并保留全部问题。一个版本内 confirmed 与未解决的同义冲突不能共存为可交付事实。P1 schema 门禁必须验证这套映射、非法组合及版本拒绝策略；示例中的 epistemicStatus 是公开格式命名，不是第二套内部确认机制。

### 8.3 模态与知识状态分离

`MUST` 表示在适用范围内必须满足；`MUST_NOT` 表示禁止；`MAY` 表示允许但不要求；`NEEDS_CONFIRMATION` 表示该选择依赖确认，相关工作不能据此执行。`MAY` 不是将未定义安全边界交给模型自由决定。

模态不等于批准。模型可以提出一项建议性的 MUST，但其 `epistemicStatus=proposed`，不能进入已确认的强制要求集合。影响业务、范围、外部依赖、数据语义、质量阈值或验收的建议，必须保留为待确认，不能因生成或语义审查通过自动升级。当前范围内为满足内容义务所必需、或会改变合同的 proposed、assumed、conflicted、unresolved 规范选择及未知适用性都应产生阻塞；明确标为非规范、非必需且不影响当前合同的可选建议可以保留可见而不阻塞。不得通过把 MUST 降级为建议、把事实状态降级或过滤未确认项缩小覆盖分母。

来源与规范程度也不同：用户原始要求、用户确认后的设计决定、模型建议、实现推导、引用资料必须可区分。来源记录应包含来源类别、可验证定位、声明主体、确认关联和适用范围；时间信息只用于追溯，不能单独证明批准。

### 8.5 已确认事实保护

现有 `guardConfirmedFacts` 已比较 Kind、Name、Content、Owner、Fields。本轮新增模态、验收、质量、范围、来源确认及其他规范 payload 后，必须纳入同一语义变更判断，否则会出现 hash 已变而授权保护未触发的漏洞。

推荐建立统一、可测试的规范语义投影，用于确认保护、差异、hash 输入和复用判断；各用途允许不同 envelope，但不能遗漏任何影响要求含义的字段。对每个新字段都应有“单独改变此字段”的反例测试。

受管理的权威定义人工编辑，继续复用 `documentflow/document_set.go` 的共享设计变更提案机制。不得直接将文档改动反向覆盖冻结事实，也不得让单篇正文产生静默分叉。

### 8.6 待决问题与关闭条件

问题继续归属于现有 questions 体系，拟增加或明确以下语义：

- 问题 ID、描述、类别、来源和关联事实。
- 受影响范围、内容义务、成员、验收与交接资源。
- 严重程度、是否阻塞、阻塞原因及允许继续的无关工作。
- 负责人或待指定责任角色；模型不得捏造现实负责人。
- 候选选项、决策依据、解决条件与所需确认。
- 状态及关闭证据；关闭不能仅是模型输出“已解决”。

问题可以因回答、明确选择、确认的不适用或获批范围调整而关闭。若调整范围，应同时更新排除项和跨范围依赖；不能删除问题来提高完整率。若问题只影响后续范围，需要形成依赖闭合且经确认的新 scoped candidate，再对该候选独立审查；不得在原全量成果集上简单忽略阻塞问题并继续定稿。原全量门禁仍按其完整范围执行。

TF-02/03 的产出是模型规范、确认保护规则、来源和问题样例；验收重点是非法引用、冲突定义、无依据确认、错误不适用和未关闭阻塞问题都能被阻断。

## 9 TF 04 类型化关系与覆盖

### 9.1 权威事实与关系投影

覆盖矩阵由规范事实和关系自动生成，不作为第二份可编辑事实表。成员文档只能引用稳定 ID 并解释，不得复制后自行改变合同字段。关系也必须有注册类型、端点限制及明确方向。

| 拟议关系 | 方向与端点 | 用途 |
| --- | --- | --- |
| `realizes` | 设计决定或模块 → 需求 | 表达设计落点与责任 |
| `constrains` | 质量或状态规则 → 接口、模块、artifact | 表达必须共同携带的约束 |
| `uses_contract` | 模块或行为 → 接口或数据 | 连接实施职责与合同 |
| `verifies` | 验收 → 需求、规则、接口、artifact | 表达具体证明对象 |
| `depends_on` | 事实 → 前置事实 | 范围拆分与影响传播 |
| `defines` | 权威成员 → 事实 | 权威归属的校验投影，不重复维护 Owner |
| `references` | 解释成员 → 事实 | 正文引用与影响定位 |
| `supersedes` | 当前新事实 → 带固定修订与摘要的历史事实 | 明确拆分、合并和替代；端点解析按第 9.4 节 |

关系名称为建议，不强制照抄。若已有关系能够准确表达，应沿用并补充语义约束。`defines` 如果由 Owner 派生，就只能生成，不能作为可独立修改字段。

### 9.2 两类图不得混同

```text
规范追踪图
需求 ← realizes ─ 模块 → uses_contract → 接口或数据
  ↑                                     ↑
verifies                              constrains
  │                                     │
验收 ───────── verifies ──────────> 状态或质量规则
  │
  └─ 预期证据要求                        artifact ← verifies ─ 交付验收

生成依赖图
范围与规范事实 → 架构成员 → 接口或模块成员 → 验收与交付成员
```

生成依赖图继续要求 DAG；规范追踪图可以存在有意义的相互约束，不应因为存在环就一律非法。对 `depends_on` 等特定关系应单独定义循环策略，避免将解释引用误作生成依赖。

### 9.3 覆盖判定算法

1. 先从经确认的范围清单固定完整要求集合及全局约束，再得到必需需求集合 `R`；不能先按 Fact.Status 过滤，再把剩余事实当作全部要求。
2. 对每个需求检查有效设计落点，不能只存在空关系。
3. 检查相关接口、状态、数据与模块是否定义且权威归属唯一。
4. 检查至少一个能够实际判定该需求的验收事实，而非只判断存在边。
5. 检查验收的方法、预期结果及证据要求完整，并覆盖适用的失败路径。
6. 检查外部依赖、跨范围依赖及明确排除项，不能因未选中就丢失。
7. 输出覆盖状态与具体缺口；分母以经确认范围为准，不能由生成器任意删除。

“100% 覆盖”同时要求关系完整和内容可判定。需求关联了无有效预期结果的验收，仍属于未覆盖。孤立的设计决定也需说明来源或明确属于实现自由度，不能自动扩展为需求。

拆分范围至少输出 `includedRequirementRefs`、`excludedRequirementRefs`、排除理由、依赖闭包及范围确认依据；这些名称是拟议字段。完整项目要求集合应保留，不能仅导出被选中的部分后宣称全项目完整。范围拆分形成新候选并单独通过确认与审查；不能借适配器选项放宽原 full-set 的未决问题门禁。

### 9.4 跨修订事实引用、替代与退役

当前 `FreezeShared` 要求关系两端存在于本次 Facts 中。新增 `supersedes` 不能靠保留失效的旧 MUST 事实凑齐端点，也不能放宽所有关系的引用校验。拟议合同如下，实际编码由 D-03/D-11 固定：

1. 当前事实仍以稳定 `factId` 定位；精确历史引用至少包含 `documentSetId`、`revisionId`、`factId`、`factHash`。修订必须是同一成果集已保留且经身份校验的祖先，不能使用 latest、同名匹配或当前可变正文。跨成果集替代不在该默认协议内，不允许猜测解析。
2. 同一事实的含义修订保留 factId，通过修订差异关联前后值；拆分/合并生成新的事实 ID，以替代记录关联旧版本。替代记录扩展既有修订/范围变更机制，保存 action、历史来源引用、当前目标引用、原因、用户确认依据、影响及覆盖说明，不建立可独立编辑的旧事实库。
3. `supersedes` 的当前端指向本候选事实，历史端按精确引用解析；一个旧事实拆为 B/C 时，记录二者共同替代 A，不能一条边就证明原 A 已全部覆盖。合并同理。单纯退役没有新目标时使用明确的退役变更记录，不伪造替代事实。
4. 替代/退役属于生命周期变更，不向 Fact.Status 添加第二套知识状态。旧事实只保存在不可变历史中；当前候选保存经确认的变更记录。当前覆盖分母仅在这份变更获确认且替代覆盖/明确排除成立后更新，所有受影响的验收、约束、依赖和解释引用须重新解析；未确认或覆盖有缺口时仍按原义务阻断，不能静默删项。
5. 普通 `realizes`、`uses_contract`、`verifies` 等关系仍要求当前端点闭合，不能通过指向已退役历史事实为当前要求计入覆盖。历史替代边只用于追踪和影响，不算新的实现/验收证明；替代链要求沿祖先版本前进、禁止环和自替代。恢复旧要求也需新的获批变更，不复用旧审批。
6. 新格式的存储、备份和恢复保留被引用的修订及必要事实闭包；清理不得删除仍可达的历史目标。公开包提供只读的历史事实描述及替代记录，含可离线重算的公开事实摘要、必要规范内容和原始身份引用，均受第 15.4 节公开载荷绑定；内部 factHash 仅作来源引用，不能冒充公开描述的可重算摘要。不要求公开私有来源原文，也不复制整条无关历史；所需闭包不可安全公开或无法解析时阻塞正式交付。

必需回归：A 拆为 B/C、A/B 合为 C、无替代退役、同 ID 正常修订和恢复旧要求；核对当前分母、旧版本可读和新旧验收归属。另覆盖错误修订/hash、非祖先、悬空/循环替代、未批准遗漏、历史目标被清理，以及离线导出和备份恢复后的引用解析。以上均是拟执行验收，当前为 NOT_RUN。

## 10 验收与质量合同

### 10.1 每项验收的最小定义

验收合同至少包含：稳定 ID、验证对象、前置环境、操作或输入、可观察结果、判定规则、验证方法、所需证据以及适用范围。条件为空时必须解释为何为空，而不是省略。

- 正向：目标行为在正常条件下成立。
- 负向：无权限、无效输入、依赖失败或禁止动作得到规定处理。
- 边界：数量、长度、超时、资源及状态临界值行为明确。
- 恢复：适用时验证重试、进程重启、重复请求与中断后的可观察结果。
- 回归：既有行为在本次变更后仍满足未改变合同。

不要求每项需求机械生成相同数量的测试；要求覆盖其真实风险。没有适用负例时需理由，不能用模板中的“无”跳过。

### 10.2 非功能约束

性能、容量和资源要求必须说明工作负载、环境、数据规模、采样窗口、统计方式、阈值和失败判断。安全要求必须说明主体、资源、权限边界、禁止行为和可验证结果。无法测量的“高性能”“安全可靠”“稳定运行”只能作为目标描述，不能直接算验收条件。

```yaml
# 拟议质量事实 payload 示例，不是已执行结果
metric: request_latency
measurement:
  environmentRef: ENV-PERF-01
  workloadRef: LOAD-01
  statistic: p95
  warmupPolicy: specified_in_LOAD-01
  measurementWindow: specified_in_LOAD-01
threshold:
  operator: less_or_equal
  value: 200
  unit: millisecond
failurePolicy: any_required_window_exceeds_threshold
status: proposed
```

数值仅是示例，不代表当前产品性能承诺。实际阈值须有用户要求或明确批准的设计依据；模型不能为了容易通过而选择宽松阈值。

### 10.3 预期证据与实际证据分离

thought-flow 保存“应提供哪些证据”；Workorch 或执行环境产生“实际证据”。公开设计中可以定义日志、测试报告、构建摘要、artifact 校验值等要求，但不能填写虚构的完成状态、构建 ID 或通过结论。

实际证据应绑定设计版本、代码提交或工作树身份、测试版本、运行环境、执行时间、工具版本和 artifact 身份。若绑定对象变化，由消费者判断失效并重验；thought-flow 不通过生成一段说明替代这一判断。

## 11 TF 05 Artifact 交付合同

artifact 不是“代码完成”的同义词。每个当前范围内的最终产物必须能回答交付什么、怎样使用、怎样检查，且不能仅用测试通过作为交付条件。

| 交付维度 | 必须定义的内容 | 例外处理 |
| --- | --- | --- |
| 形态与边界 | 源码包、二进制、镜像、网站、库或组合 | 多种形态分别列明 |
| 内容清单 | 必需文件、入口、资源、说明和版本信息 | 不含项明确排除 |
| 构建 | 工具链、命令、依赖解析、可复现要求 | 不需构建则说明 |
| 运行 | 启动方式、参数、配置、工作目录 | 秘密值不写入设计包 |
| 环境 | OS、架构、运行时、外部服务版本范围 | 不支持环境明确列出 |
| 数据 | 初始化、持久化、迁移、备份、恢复要求 | 仅在适用时强制 |
| 用户使用 | 最短使用路径、错误处理、限制 | 与目标用户能力匹配 |
| 安全与许可 | 依赖许可、敏感信息、权限和分发限制 | 是否适用需明确 |
| 验证与身份 | 构建、运行、行为及文件校验要求 | 由真实执行产生结果 |

artifact 规范作为权威事实或其类型化 payload 存在，交付章节与检查清单由该事实生成。不得在 README、交付文档和验收表中维护三份不同要求。

TF-05 验收包括缺入口、缺运行环境、依赖配置不明确、产物与测试对象不一致等反例。thought-flow 负责阻止“不知道最终交付什么”的设计定稿；实际构建、运行与产物同一性由 Workorch 验证。

## 12 TF 06 工程生成规则

### 12.1 用途隔离

为工程成果集引入明确的生成意图或 Profile 能力声明，具体字段待实施设计确认。优先从文档集调用链传入，不修改一般 Capture 的全局默认策略。需要覆盖首次生成、重试、修复、重新生成和单篇受管编辑回流，不只覆盖正常生成路径。

工程用途的 `completeDocumentDraft` 类补全不得用通用段落、原始 Capture 堆叠或空泛说明将关键章节伪装为完成。可保留草稿骨架，但必须产生结构化缺口并阻断相应门禁。一般归档的既有补全行为应按原用途回归。

### 12.2 每次生成的固定输入

- 文档集、计划、修订、Profile 及候选身份。
- 成员角色、必答内容、适用条件与权威定义归属。
- 当前范围、必须携带的全局合同、明确排除项。
- 该成员相关的规范事实、来源状态、未决问题及允许自由度。
- 冻结上游成员正文与对应 hash，不能读取随时变化的 latest 替代。
- 允许修改的内容范围、确认保护规则、输出结构与失败协议。
- 模型与提示词身份、调用预算和可追踪尝试 ID。

上下文应可从持久状态重新构建。摘要只能辅助理解，不得替代权威合同。若关键上下文超限，应调整范围、减少非必要解释或明确阻塞；不得悄悄删掉必需约束。

### 12.3 输出与失败处理

输出至少分为正文、规范事实引用、内容义务落点、缺口和建议变更。模型不直接提交获批事实变更；涉及合同变化时输出提案，进入现有修订与确认流程。

| 情况 | 正确处理 | 禁止行为 |
| --- | --- | --- |
| 关键事实缺失 | 标记具体缺口和受影响义务 | 自行编造需求 |
| 上游矛盾 | 提交冲突并阻断依赖工作 | 任意选择一个解释 |
| 未知适用条件 | 保留待决问题 | 当作不适用 |
| 模型输出结构非法 | 记录失败，预算内可修复 | 接受解析丢字段后的结果 |
| 空章节 | 保留未完成状态或失败 | 填通用段落后标完成 |
| 需要新增外部依赖 | 形成需确认建议 | 直接加入强制实现 |
| 修复触及已确认事实 | 走提案与授权保护 | 借修复绕过确认 |

继续复用现有 DAG、调用预算、失败记录和有限修复，不新增无限重试机制。重试应保持绑定身份；当前 ModelHash 变化会被拒绝，不得为了评估跨模型而放松生产重试约束。

### 12.4 产出与验收

产出包括角色化生成契约、上下文规范、缺口结构、提示词版本策略和用途隔离测试。主要落点为 `documentsetflow/service.go`、`repair.go`、`calls.go`、`ai/document_set.go` 与 `ai/refiner.go`。

验收必须包含正常样例和失败样例；要求工程模式暴露缺口，同时普通笔记、单篇 Capture、研究文档保持既有用途行为。仅检查模型返回非空正文不算通过。

### 12.5 并发 重复请求与迟到结果

以下是拟增强的行为合同，不宣称基线已覆盖全部边界。推荐复用现有运行和成员身份，在请求开始时固定候选、输入、依赖、Profile、模型与操作身份，在结果应用时再次检查；不要另设脱离主流程的生成状态库。

1. 开始前比较请求的预期修订与当前修订，过期请求拒绝执行，不自动应用到新版本。
2. 同一操作身份的重复请求返回已有进行中或完成记录，不重复发起模型调用或产生第二份规范结果。
3. 模型返回后以 compare-and-swap 语义校验当前候选及成员输入身份；期间已修改、取消或被替代的结果只记为迟到/失效，不覆盖当前成员。
4. 对已完成同一输入的重复应用应无副作用；语义无变化的修订返回 no-op，不伪造一个已变化版本或重新授予审查通过。
5. 写入正文、成员结果与身份引用需具备原子提交或可恢复协议，部分写入不得显示成员成功。
6. 正式冻结内容及已导出字节不原地修改；重新生成形成新候选或新导出身份，旧文件仍可核验。

操作去重不表示自动重试所有失败。已知外部调用成功但本地结果不明时，先检查已保存状态再决定重试，避免无意重复费用和不一致结果。测试应覆盖重复点击、响应乱序、生成中人工修改、取消后返回、重启后重放及持久化中断。

## 13 TF 07 独立质量门禁

### 13.1 复用门禁而非新增旁路

现有 Ready、Finalize、Export 门禁、结构验证、语义审查和人工审查继续作为主链路。新规则接入现有候选身份与审查绑定，不能另建一个只检查交接文本的成功路径。

| 门禁层 | 检查内容 | 失败时的结果 |
| --- | --- | --- |
| G0 输入与 schema | 字段类型、枚举、引用、来源和必要上下文 | 规划或候选无效 |
| G1 规范一致性 | 唯一权威、合同冲突、模态、确认状态 | 不可 Ready |
| G2 内容与覆盖 | 必答内容、设计落点、验收与范围 | 不可 Ready 或要求修订 |
| G3 语义质量 | 行为明确、可实现、可验证、失败路径、交付完整 | 语义审查失败或待处理 |
| G4 人工确认 | 待决问题、例外、范围与实质合同变更 | 不可 Finalize |
| G5 冻结与导出 | 当前身份、有效审查、公开投影、文件一致性 | 不可 delivery/交接 |

具体在哪个既有入口判定由实现决定，但同一失败不能在另一个入口被忽略。diagnostic 和 backup 可满足各自用途，不代表 delivery 合格。

### 13.2 审查独立性

生成器输出“自评通过”不能作为门禁依据。确定性校验由程序执行；语义审查使用独立输入、审查任务和候选绑定，审查结果需要可定位的理由。可在成本允许时使用独立模型或不同提示策略，但模型不同本身也不证明正确。

实现模型或生成模型不得修改原验收、删除负例或放宽阈值以通过检查。发现验收错误应形成独立变更，经确认后生成新基线并重新审查。

### 13.3 规则结果结构

拟议检查结果应包含 `ruleId`、严重级别、状态、消息、事实 ID、成员 ID、正文锚点或字段路径、修复建议和绑定候选。字段路径应相对稳定事实 ID 定位，不把易变化的数组下标作为唯一定位方式。

状态至少区分 `NOT_RUN`、`RUNNING`、`PASS`、`FAIL`、`ERROR`、`STALE`、`NOT_APPLICABLE`。`ERROR` 是检查未完成，不是发现内容合格；`STALE` 是旧结论，不得与 PASS 合并展示。

语义审查即使没有发现问题，也不能覆盖确定性失败。人工确认也不能无记录地豁免强制 schema、来源真实性或 hash 完整性；可接受的产品例外需独立记录范围、原因和批准依据。

### 13.4 必须具备的反例

至少拦截：标题齐全但无行为、验收无判定条件、接口同名不同约束、遗漏失败路径、质量阈值无测量条件、模型建议伪装用户要求、artifact 无运行入口、阻塞问题未关闭、正文与规范事实矛盾、审查绑定旧候选。

对每个反例记录预期触发规则与定位点。不能因为语义模型偶然发现同类问题，就省略能够程序化的确定性规则。

## 14 TF 08 修订影响与身份安全

### 14.1 复用现有修订机制

`repair.go` 已有上游修复后的下游处理与确认事实保护；`documentflow/document_set.go` 已将受管权威定义编辑转为共享设计变更提案。本轮重点是扩展语义和可解释影响，不重新建设变更管理。

修订应形成旧基线、新候选、差异与原因，旧冻结版本保持可识别。禁止直接改写旧定稿或将新正文塞入旧候选 hash 下。

### 14.2 影响闭包

```text
事实或 Profile 改变
  → 规范语义差异
  → 关联需求 接口 数据 规则 验收 artifact
  → 权威成员及引用成员
  → 生成 DAG 下游成员
  → 覆盖矩阵 规则报告 语义审查 人工确认
  → 公开设计包和 Workorch 交接预览
```

影响计算以类型化关系和成员依赖为依据。对无法可靠定位影响的变更，应保守扩大失效范围并说明原因，不能默认“未受影响”。展示哪些必须重生成、只需重新校验、需要重新确认和可安全复用。

### 14.3 可复用条件

复用必须有可验证谓词：规范输入未变、Profile 相关义务未变、角色和上下游身份满足原约束、生成或验证算法版本适用、没有新增阻塞问题。不能以正文“看起来差不多”复用旧通过记录。

可复用正文不等于可复用审查；正文未变但规则版本变化时，可能仍需重新验证。未受影响成员可以保留内容，但整包候选身份、汇总覆盖和导出应重新计算并绑定。

### 14.4 新字段必须同步纳入的路径

| 路径 | 收口要求 |
| --- | --- |
| 规划与冻结 | 新语义解析、白名单及规范化一致 |
| hash 与身份 | 所有影响含义的新增字段参与规范身份 |
| 确认保护 | 新字段变化不能绕过已确认事实保护 |
| 权威正文渲染 | payload、模态和适用范围可被准确呈现 |
| 结构和语义审查 | 新字段有明确规则，不只序列化 |
| 影响与复用 | 新字段变化导致应有的失效 |
| 导出与公开投影 | 仅导出批准公开的合同语义 |
| 备份与恢复 | 保留正式语义并校验版本与完整性 |

这是一个不可拆散的实施清单；任何一列遗漏，都可能形成“存得下但无法可信使用”的半成品。

### 14.5 版本边界与已豁免的历史兼容

基线存储 schema 为 `1`，读取时会重新计算内容身份，`CandidateHash` 包含 `ValidatorVersion`。因此仅提升验证器版本，也可能让历史读取因重算 hash 不一致而失败；不能声称“只加字段所以向后兼容”。

按第 2.4 节已有用户决定，旧格式向后兼容、旧记录迁移、旧版只读及旧 hash 重算均不是本轮必做项。P0 要固定新格式声明支持的 schema/ValidatorVersion/公开格式组合与安全拒绝规则，不再把实现旧版本适配作为进入 P1 的前提。若检查算法变化，必须明确是受支持版本的身份重算还是需要新候选和新审查，不能以全局当前常量任意重解释记录。

禁止通过忽略 hash 检查、把历史 ValidatorVersion 改为当前值或批量重写历史 hash 消除报错。迁移若被选择，必须有备份、干跑结果、冲突报告、原子性、失败恢复与回滚验证；实际执行需单独授权。

不得清空已有工作区或删除历史数据来让新 schema 测试通过。验收以新格式内的修订、定稿、备份/恢复及不支持版本的明确拒绝为准；旧格式样例用于证明安全拒绝与原字节保留，不要求恢复为可用对象。第 9.4 节引用的新格式历史必须保持可达，不能以本节豁免为由丢弃。未来若另行启用兼容或迁移，应先扩展范围与测试，不回写本轮已有通过结论。

## 15 TF 09 公开设计包

### 15.1 三种包保持分离

| 包类型 | 用途 | 不得推导的能力 |
| --- | --- | --- |
| delivery | 经有效门禁的正式设计交付 | 不代表 Workorch 已批准执行 |
| diagnostic | 故障与问题分析 | 不代表可实施或正式定稿 |
| backup | 完整恢复所需备份 | 不代表可公开或通用设计导入 |

当前 Import 只接受 backup；不得将新增公开设计 JSON 冒充 backup 或宣称其已能直接导入 Workorch。

### 15.2 拟议交付内容

现有 Markdown、HTML、索引、审查和 manifest 继续保留。建议扩展以下派生文件，名称需在实现前确认，均不是基线已有能力声明：

```text
<delivery-root>/
  index.md                         # 现有索引能力继续使用
  documents/...                    # 固定版本的可读文档
  manifest.json                    # 扩展现有清单而非另建身份源
  public-payload.json              # 拟新增 冻结公开载荷描述符，不把自身列入被摘要文件表
  design-contract.json             # 拟新增 公开规范事实与类型化关系
  coverage.json                    # 拟新增 由同一事实图派生的覆盖结果
  scope.json                       # 拟新增 当前范围 排除项 跨范围依赖
  review/...                       # 有效且允许公开的审查投影
  resources/...                    # 经审核的必要公开资源
```

可将 scope 和 coverage 合并入统一公开合同，但不得重复存储可独立编辑的规范事实。若保留单独文件，应在 manifest 标记其派生来源与身份，独立检查器必须验证一致性。

### 15.3 公开投影规则

现有 BuildPlan 已去除消息正文和精确来源引文，但其内部身份结构仍有 Capture 元数据等不应直接公开的字段。应复用既有隐私意图并构造明确的公开投影，而非把内部计划当作完整公开 DTO 直接 `json.Marshal`。拟新增公开字段必须采用允许列表，内部新字段默认不公开。

- 保留需求和确认的来源类别、稳定公共引用和必要说明，不包含私有原文。
- 不导出 Capture、私有会话、内部提示词、密钥、文件系统敏感路径或无授权资源。
- public provenance 可以证明“该要求来源于何类确认”，但不伪造公开用户身份或批准凭证。
- 公开审查报告删除私有上下文，只保留必要结论、定位、限制和身份。
- 资源按实际内容做隐私检查，不能只检查文件名或扩展名。
- 权威定义和正文不得因脱敏改变语义；无法安全公开的必需合同导致交付阻塞。

公开规范陈述与私有来源引文是不同对象。用户已批准公开的要求正文可以完整保留，即使其中措辞与用户输入相同；不能因此附带整个消息、周边对话或来源引文。若没有公开许可或包含敏感内容，应阻塞并提出处理选项，不将其悄悄改写成“用户原文”。

### 15.4 Manifest 与独立校验

manifest 应标识包类型、格式版本、文档集与定稿身份、Profile 和校验策略身份、文件路径、字节大小、内容 hash、生成工具版本及公开投影版本。具体字段为拟议扩展，不能与已有 manifest 字段重复定义冲突语义。

文件 hash 计算必须明确算法及输入字节；正文应统一 UTF-8 与换行策略。manifest 不应要求包含自身 hash 而形成循环；可由外层包摘要或单独校验值绑定整个包。hash 只证明内容一致性，不自动证明发布者真实性或执行授权。

独立校验器至少检查：安全相对路径、文件缺失或多余、大小及 hash、schema、引用闭合、范围一致、正文权威锚点、候选与审查绑定、公开字段允许列表。缺文件、跨版本混用或内容被修改必须可发现。

#### 15.4.1 三类身份与无循环绑定

内部 `CandidateHash` 由计划、成员及 ValidatorVersion 等计算；内部修订 hash 还包含审查报告。公开投影删除内部字段，Markdown/HTML 又会改写链接，因此内部 hash 不可从公开包直接重算。不能要求独立检查器以缺失的私有对象验证内部 hash，也不能为方便验证导出私有计划。

本轮采用以下拟议合同；字段名可在 D-12 中统一，但身份职责及依赖方向不得省略：

| 身份 | 摘要输入与作用 | 离线验证边界 |
| --- | --- | --- |
| 内部候选/修订身份 | 既有冻结计划、成员、校验策略及审查 | 包中只作固定来源引用，不宣称可由公开文件重算 |
| `publicPayloadHash` | 版本化公开描述符：规范合同、范围、覆盖、必要历史描述、Profile/策略公开快照、成员文件及资源的路径/大小/hash、转换映射 | 必须仅由公开内容和公开规范算法重算，作为公开审查的精确对象 |
| 分发身份 | 完整导出文件清单，以及分发 ZIP 的实际字节摘要 | 包括公开审查文件；ZIP 摘要置于包外回执或可信渠道，避免自包含循环 |

公开载荷描述符不包含其自身摘要、审查结果/审查 hash、内部修订 hash、定稿 hash、分发清单 hash 或 ZIP hash。内部候选身份可在审查绑定中记录，不进入该公开载荷摘要。公开描述符包含固定 set/revision ID 及必要语义版本；所有所需规范输入须由允许列表明确列出，不能靠摘要字段省略本应公开的合同。

描述符文件不列入自己的被摘要文件表；分发 manifest 再记录描述符文件的实际字节摘要。`publicPayloadHash = "sha256:" + hex(SHA256(canonicalPublicJSON(descriptor)))`，规范化算法版本在 descriptor 中固定，descriptor 不含 publicPayloadHash 字段。公开报告引用该值；publicReviewHash 对不含自身 hash 字段的公开报告计算，置于分发清单/回执，不回写进公开载荷。这样公开载荷、审查、分发身份分别可重算，且没有摘要自引用。

拟议依赖顺序如下，不将新增公开摘要写回 Plan/Members 造成 CandidateHash 自引用：

```text
冻结计划/成员 → 内部 CandidateHash
冻结公开文件与描述符 → publicPayloadHash
CandidateHash + publicPayloadHash + 审查策略 → 最终审查报告
内部报告 + 内部候选 → 内部 RevisionHash → 定稿绑定
公开审查投影（绑定上述公开摘要及固定来源引用） → publicReviewHash
公开载荷 + 公开审查文件 → 分发 manifest → 外部 ZIP 摘要
```

最终审查前必须形成并冻结公开载荷；审查者/检查器核对规范事实、正文及公开投影一致后，把 publicPayloadHash 和投影/规则版本记入报告。Ready、Finalize 和 delivery 必须重验该绑定。若投影、正文转换、资源或规则改变，应重新形成候选/审查，不能在导出时给旧 PASS 临时补一个新摘要。最终审查报告和公开报告各自的 hash 都排除自身 hash 字段，内部报告 hash 作为公开来源引用时不参与公开载荷摘要，避免循环。

本节新增绑定适用于本轮工程设计公开交付用途，以显式用途/Profile 能力接入；一般归档和研究仍按其既有规则。工程草稿/诊断可在绑定未完成时保存，但不能借一般导出入口声明为本节正式设计 delivery。

#### 15.4.2 公开规范化、正文转换与检查顺序

- 公开语义 JSON 的首版规范编码采用 RFC 8785 JCS，并以 `public-json-jcs-v1` 标识：UTF-8、无 BOM、拒绝重复/未知键及非有限数；对象键按 JCS 的 UTF-16 码元顺序排列，数组维持 schema 规定的语义顺序，不随意排序或去重。schema 数字限定于能无损处理的安全整数范围；更大的计数/身份值使用规定的十进制字符串，不允许舍入。字段省略、null、空数组/对象在 schema 中逐项固定，不能依赖某种语言默认序列化。字符串不额外 trim、不做 Unicode 归一化或偷偷改变换行；需有 Go/JavaScript 等跨实现规范化向量，不能以普通 json.Marshal 结果直接冒充 JCS。
- 文件摘要采用 SHA-256，输入为冻结的实际文件字节；路径使用安全、唯一的 `/` 相对路径，并固定大小写及 Unicode 路径冲突拒绝策略。正文的 UTF-8/LF 规则在冻结前应用；二进制资源不做文本归一化。manifest 校验阶段不再改写任何字节。
- 描述符保存每个成员的规范公开正文、最终 Markdown/HTML 的路径和摘要，以及逻辑引用到成员文件/锚点、resource ID 到公开资源文件的确定性映射。原始内部 BodyHash 仅作来源引用；离线检查用公开规范正文和版本化转换规则复核派生字节，不错误地要求改写后正文匹配原 BodyHash。
- 渲染/转换规则及 Profile/检查策略的可公开内容或公开格式定义必须足以离线解释；不能只给一个消费者无法取得的内部版本号。实现可保存冻结公开文件，或提供能复现相同字节的受支持转换器。升级渲染器后不能在同一 publicPayloadHash 下重新产生不同 HTML；无法取得匹配字节时拒绝正式导出。
- 检查器依次核对文件集合/路径/大小/摘要、公开描述符规范摘要、规范合同与范围/覆盖/历史引用闭合、转换映射与派生正文、公开审查的 publicPayloadHash/策略/状态，再检查 manifest 与公开审查摘要。覆盖/范围等派生文件必须按同一合同重算，不仅比较文件自带的摘要。

若将包 A 的合同/正文与包 B 的审查混合，即使重算文件清单，公开摘要与审查绑定仍须失败。需要包含正常离线包、链接改写、旧转换规则、历史描述，以及只改合同/只换审查/跨版本资源等反例。

包内 hash 只能检查一致性。若连同合同、审查和清单全部伪造重算，不能仅凭包内数据证明原发布者或批准真实性；需由可信渠道提供预先固定的 publicPayloadHash 或分发摘要后核对。签名体系不是本轮默认新增范围，无可信外部锚点时不得把“内部一致”写成“已认证发布者”。

### 15.5 产出与验收

主要落点为 `documentsetstore/packages.go`、`store.go`、`import_paths.go` 和应用导出服务。公开投影可作为新模块，但目录与公开 API 在设计审查后确定。

验收以离开 thought-flow 的文件副本为对象：只靠该包及公开格式说明即可阅读、解析、检查引用与校验内容。成功导出 zip 但无法独立解释合同，不算完成。

## 16 TF 10 Workorch 专用交接适配

### 16.1 完整设计包与有界交接不是同一物

完整设计包保存全部经确认设计及追溯信息；Workorch handoff 只承载本次确认范围所需的有界输入。适配器是派生层，不重新确认要求、不放宽验收，也不替代 Workorch 自身创作、审查和批准流程。

当前 Workorch 的实际通用设计包导入器未得到验证。本轮按现有文本资源入口设计，不以新增导入 API 为前提。下文为适配方案，不是已实现接口承诺。

### 16.2 当前输入约束

以下以固定 Workorch 提交为准，单位按 UTF-8 字节计，不能使用 JavaScript 字符串长度或中文字数替代。

| 输入 | 上限或规则 |
| --- | --- |
| `GoalText` | 最大 32 KiB，即 32,768 bytes |
| `AcceptanceRequirements` 条目数 | 最多 128 条 |
| 单条 `AcceptanceRequirements` | 最大 4,096 bytes |
| `TemplateID` 与 `WorkspaceID` | 各最大 256 bytes；真实工作区身份由消费者提供 |
| 相关输入总量 | 最大 128 KiB，即 131,072 bytes，按下述精确公式 |
| 有序 `ResourceRefs` 数量 | 最多 8 份；每个引用最大 1,024 bytes，规范化后不得重复 |
| 单份文本资源 | UTF-8，最大 32 KiB |
| 全部文本资源 | 合计最大 128 KiB |
| 资源位置 | 必须位于 `DeliverableDirectory` 允许范围内 |
| 资源来源 | 不接受任意远程 URL 作为该入口资源 |

消费者先对 GoalText、TemplateID、每条 AcceptanceRequirements 和每个 ResourceRef 做 TrimSpace；WorkspaceID 不在该规范化函数中 trim。上述各文本必须非空、有效 UTF-8 且不含 NUL。要求列表允许为空，但不能将本应携带的验收删除来利用这一结构容许。资源引用保留顺序，规范化后重复引用直接被拒绝。

```text
normalizedInputBytes = bytes(GoalText) + bytes(TemplateID) + bytes(WorkspaceID)
                     + Σ bytes(AcceptanceRequirements[i])
                     + Σ bytes(ResourceRefs[i])
normalizedInputBytes <= 131072
resourceSnapshotBytes = Σ bytes(actualResourceContent[i]) <= 131072
```

输入公式不包含 JSON envelope、Version、Revision 或资源正文；资源正文另受单份/总量限制。当前输入 Version 必须为 1，Revision 必须大于 0，WorkspaceID 必须来自真实消费者上下文。适配器不得伪造这些身份来产出“有效请求”；尚未连接消费者时，只能给出材料预算和待绑定字段，不能宣称消费者请求已通过校验。输入 hash 还绑定 revision 和原有顺序，不能通过排序、去重或 A→B→A 内容回退复用旧确认。

输入总量与资源总量必须分别检查。测试复用或严格对齐上述实际计算方式；后续版本若改变口径，应显式升级适配版本而非选择较宽松解释。

#### 16.2.1 模板与派生验收的合并预算

通过 `DefinitionAuthoringInput.Validate` 不等于后续创作可执行。固定消费者的 `DefinitionDerivedAcceptance.ValidateFor` 还将直接验收、真实模板 DoDItems 和派生 AdditionalItems 共同计入以下预算：

```text
mergedAcceptanceBytes = Σ bytes(input.AcceptanceRequirements[i])
                      + Σ bytes(template.DoDItems[j])
                      + Σ bytes(derived.AdditionalItems[k])
mergedAcceptanceBytes <= 131072
```

每条非空、有效 UTF-8、不含 NUL且不超过 4,096 bytes；AdditionalItems 自身最多 128 条，直接验收仍受输入条数限制。不凭此公式杜撰“全部候选合计最多 128 条”的限制。合并检查应复用消费者实际检查时的规范化/原始文本规则；不能通过额外 trim 或摘要改写扩大预算。

例如 32 条各 4,000-byte 的直接验收，加 37-byte 的 Goal/TemplateID/WorkspaceID，输入共 128,037 bytes，满足输入预算；真实模板再有一条 4,096-byte 验收，即使没有派生项，合并验收已为 132,096 bytes，必须提前阻塞。不能将这种输入显示为“可直接完成消费者创作”。

适配预览在尚未绑定真实模板时只显示输入/资源测量值和模板待绑定状态。取得消费者提供的 TemplateID、模板快照/hash 后，先检查直接验收与模板的已知下界；已超限立即阻塞。设计资源中需要派生提取的必需验收也应列入承载及预计占用分析，但预测不冒充消费者实际结果。AdditionalItems 只有消费者产生并封存后才有精确文本；在此之前合并总量标为待验证，之后由消费者按实际三部分重新校验，并回传真实引用与结果。

模板快照或派生结果变化使原预算结论与相应输入确认失效。预留余量可以是解释性策略，不能替代实际边界检查，更不能删除模板条目、丢失资源中的必需验收或要求模型删项来让数字通过。

#### 16.2.2 请求组装预算与状态分层

固定消费者的派生、提案及审查请求还检查序列化 payload 与合同/提示的组装大小，当前 `maxDocumentBytes` 为 256 KiB。JSON 转义、真实模板、资源正文、Profile 合同、候选与审查材料都可能占用预算；该限制不同于上面的 128 KiB 输入/资源/合并验收限制，不能直接相加后宣称全部流程适用同一上限。

生产端只检查自己持有精确材料的层：输入、资源计划、已知模板下界与承载覆盖。消费者对实际各阶段请求组装再次检查；模板、派生结果或提示合同尚不可用时，预览清楚列出相应待验证项。状态至少区分“材料可导出”“消费者输入/资源待验证”“合并验收/请求组装待验证”“实际消费者创作及审查已验证”，不把其中任一层通过升格为后续层通过。端到端预算验证归 AC-30/35 的消费者层，本地生产端仍可按第 24 节独立验收。

### 16.3 要求映射与身份边界

| 交接内容 | 来源 | 强制保留的区别 |
| --- | --- | --- |
| 本次 Goal | 当前确认范围与目标事实 | 不把全项目目标伪装成本次可完成范围 |
| 原始用户验收要求 | 可追溯的用户要求 | 不能被模型改写后标为原文 |
| 候选补充验收要求 | 设计推导、风险补充、测试建议 | 明确候选与待批准状态 |
| 必要资源 | 冻结公开设计、依赖和约束 | 顺序、版本和内容身份固定 |
| 需求映射 | 设计事实 ID 到交接条目 | 不是 Workorch 正式 DoD 映射已成立 |

`ResourceIDs`、`SourceItemRefs`、`DoDItemRefs` 是不同领域的身份概念。适配器不得把设计事实 ID 填入任何一个字段来假装该对象已由 Workorch 创建，也不得自行生成批准记录或 Run。

可输出 `sourceDesignFactRefs` 等明确属于适配层的映射字段，最终名称待确认。Workorch 接受输入后产生的正式 ID，只能来自它的真实返回值或持久记录。

#### 16.3.1 固定消费者字段映射与确认边界

固定消费者会把 `AcceptanceRequirements` 原样生成 `derived-dod:user:*`，后续分类为 `USER_EXPLICIT`；GoalText 同样作为独立用户目标保留。这不是一个支持任意来源标签的通用验收数组，给字符串加上“设计建议”前缀也不能改变分类。默认映射如下：

| 生产端对象 | 现有消费者通道 | 必需约束 |
| --- | --- | --- |
| 按确认范围编排的目标 | GoalText 预览；消费者用户精确确认后成为正式输入 | 仅确认范围不等于确认编排后的 Goal 原文；记录来源映射和实际确认字节/hash |
| 消费者用户直接提供或明确选定为本次直接输入的验收 | AcceptanceRequirements | 逐项固定完整文本、顺序、来源及确认依据；自动抽取不算用户直接输入 |
| 来自已定稿设计的要求、约束及可判定验收 | 带来源、事实 ID、确认状态和模态的文本资源 | 即使在 ThoughtFlow 已 confirmed，也不自动转为消费者 USER_EXPLICIT；按消费者现有派生路径提取并审查 |
| 风险补充或模型建议 | 资源中的候选补充区 | 不填入 AcceptanceRequirements；消费者可形成 AdditionalItems，其身份只取自真实结果，仍需自身审查/确认 |
| 真实模板的约束 | 消费者封存模板 | 不伪装成用户输入，也不为减少预算在生产端重写或删除 |

当没有本次消费者直接输入的验收时，AcceptanceRequirements 可以为空，前提是全部设计必需验收已完整进入有序资源并有逐项映射；这不是允许删掉验收。资源提取经消费者处理为 DERIVED，不改变它在设计域中“已确认要求”的事实。两个领域的来源状态并列保存，不能互相覆盖；尚无真实派生结果时，覆盖验证为待消费者验证。

消费者用户若主动把某个设计条目选为本次直接要求，记录这是“消费者在本次输入中明确采用”，并保留设计来源及原事实关联，不能回写为 ThoughtFlow 原始用户陈述。该操作确认具体规范化文本/顺序和当前输入 revision，不自动授予 DoD、运行或执行权限。用户还须具备相应公开权限；不能为满足逐字传递而把私有消息放入资源。

#### 16.3.2 逐项映射及拒绝条件

适配层映射至少记录：固定设计引用、设计来源类别/状态/模态、公开要求文本摘要、传输通道（Goal、直接验收或资源）、条目序号或稳定资源锚点、传输字节摘要、消费者确认状态/依据，以及真实接收后产生的 candidate/requirement/obligation 引用。未返回的消费者 ID 保持未绑定，不用设计 ID 或推算序号占位。

真实派生和审查后必须逐项核对：所有当前范围必需合同被完整承接，来源未被升级，原条件/负路径/阈值未被改写，分组未丢失单项义务。遗漏、歧义、预算拒绝或来源错分均阻塞 HC 验证；不能因为完整 Goal 或资源文件仍存在就判逐项覆盖通过。

范围确认、消费者精确输入确认、规格/DoD 批准和执行授权分别记录。任何一层文本、顺序、模板或 revision 改变，都应按消费者规则重新判断确认有效性。生产端无权代写这些确认。AC-33 必须通过真实消费者证明混合来源仍保持正确分类，不能仅断言生产端 JSON 多了一个 source 字段。

### 16.4 拟议适配流程

1. 读取通过文档集级门禁的定稿，不走普通 Topic 导出旁路。
2. 固定定稿身份、publicPayloadHash、分发摘要和所选范围。
3. 计算必需需求、全局约束、依赖闭包、验收和 artifact 要求。
4. 按第 16.3 节生成 Goal、直接验收/设计资源/候选补充的通道映射与有序资源计划，不自动将设计抽取项填入直接验收字段。
5. 计算每个字段及资源的 UTF-8 字节数、数量；绑定真实模板后检查合并验收已知下界，明确实际派生及请求组装的待验证预算。
6. 检查每项必需合同有承载位置；不能只检查总大小。
7. 生成预览、缺口、超限原因及分层状态，区分材料可导出与消费者创作已验证。
8. 用户确认范围并具备公开授权后，才允许导出该范围材料；若尚无消费者精确输入确认，只能标为待确认草案，不宣称是已获确认的消费者请求。
9. 实际提交、模板/派生/请求预算复验、规格批准及执行仍遵循 Workorch 流程，不因导出自动发生。

### 16.5 超限策略

超限必须阻塞，不允许静默截断、删除难实现要求、丢弃负路径或降级质量阈值。可以去除非规范重复解释，但必须证明保留规范语义；不能用摘要替代不可遗漏合同。

若仍超限，可提出业务闭环拆分：每包包含已确认范围、明确排除项、完整全局约束、必要依赖和验收；跨阶段前置条件必须可见。范围确认前只能预览，不能宣称该缩小范围已获授权。

规范化后重复资源引用已被当前消费者拒绝，适配器应提前定位重复项，不静默去重。BOM 与换行属于实际文件字节，应按消费者实际读取结果计数并校验 UTF-8，不能凭适配器自定义较宽松口径。

文件必须按消费者认可的方式放置，并由其 File owner 实际读取和校验，在消费者实际 DeliverableDirectory 中具备正确归属与可读性；不要求只负责读取的 File owner 同时承担文件创建职责。导出端相对路径合法，不证明另一个主机上的文件已存在或可读；适配器不能声称验证了不可访问环境。消费者校验必须阻断路径穿越、符号链接（包括目录内链接）、挂载边界跨越、链接 inode、归属不符、交接期间内容变化及 hash 不匹配；读取后应绑定实际读取的字节身份，不能只校验路径字符串。无法检查实际落地资源时，交接状态保持待消费者验证。

### 16.6 验收与限制

验收包含 8/9 份、32 KiB 边界及超一字节、各层 128 KiB 边界、多字节中文、非法 UTF-8、路径逃逸、任意 URL、缺依赖、未确认范围、重复 ID 和伪造状态等案例。另包含输入通过但模板合并后超限、模板未知、实际派生结果超限、请求组装超限，以及原始输入/设计抽取/候选补充混合来源；不得用前一层通过掩盖后一层未验证。

通过生产端适配校验只说明“材料满足本地可检查的提交条件”；实际文件落地、接收和理解仍需 P4-HC 联合验证，更不说明最终 artifact 符合要求。后者需要消费者实施与独立验收证据，不属于 ThoughtFlow 生产端本地完成条件。

### 16.7 HC-1 设计交接候选共同边界

**合同状态：HC-1 设计交接候选，本文为评审修订 r1。** 这是两项目共同评审和实施的拟议边界，不是已经存在的 JSON schema、导入 API、执行协议或已完成联调。两份分册独立说明自身实现；以下 HC ID、语义及预算必须保持一致。本次只修改 ThoughtFlow 分册，公开身份、来源通道和后续预算的补充待 Workorch 分册同步评审，未完成前保持候选状态，不宣称双方已采用。最终字段名、版本和适配入口在双方评审后固定，修改时同步版本与测试，不能单方静默重解释。

完整、不可变的公开设计基线与有界 Workorch 创作材料是两层对象。前者保存全量已声明范围及对应合同和追踪；后者是某个已确认范围的派生输入。资源不足不得反向削减完整设计基线，公开包也不得混入私有内部计划。

| HC ID | 共同不变量 | ThoughtFlow 生产端责任 | Workorch 消费端责任 |
| --- | --- | --- | --- |
| HC-01 | 语义身份、文件字节身份与固定设计基线一致 | 固定文档集、修订、候选/定稿、Profile、验证策略及公开投影版本；按第 15.4 节冻结公开载荷摘要与审查绑定 | 离线重算公开摘要并核对审查、转换及资源；内部 hash 仅作来源引用；创建真实消费者对象后记录映射，不以 latest 或同名文件替代 |
| HC-02 | 要求来源、确认状态、模态与覆盖分母不可偷换 | 分开用户原始要求、已确认设计决定、候选补充、假设和冲突；保留范围、排除理由、全局约束与依赖闭包 | 保留这些差别并检查派生覆盖；未确认的规范选择不能升级为正式要求，不能删去难项制造完整率 |
| HC-03 | 公开投影按允许列表生成且不改变规范含义 | 清除私有 Capture、对话与来源原文、内部提示词、秘密、敏感路径及无权公开资源；检查正文和实际资源 | 不因文件来自设计包就信任其中嵌入指令；按资源和隐私边界接收，发现必须内容不可安全公开时阻塞 |
| HC-04 | 输入、资源、合并验收及请求组装预算分层检查 | 按固定版本计算精确字节/条数/顺序，绑定真实模板后检查已知下界；未知派生/请求材料保持待验证 | 对真实输入、资源、模板、派生结果及各阶段请求复验；不能用截断、静默去重、伪造身份或放宽口径通过 |
| HC-05 | 安全导出不等于安全落地 | 生成安全相对路径与内容身份，明确待物化资源和环境未知项，不声称已验证远端落地 | 由 File owner 在真实 DeliverableDirectory 内实际读取、核对归属与字节；拒绝路径穿越、符号链接（包括目录内链接）、挂载边界跨越、链接 inode、读取期变更或 hash 不符 |
| HC-06 | 设计就绪不构成批准、执行或证据 | 只声明设计候选/定稿及生产端检查；不生成 Workorch 批准、DoD、Run 或实际执行结果 | 通过自身正式创作、审查、批准及权限流程；独立取得所需执行授权，实际结果只能来自真实执行 |
| HC-07 | 设计变更形成新候选并使受影响派生结论失效 | 保留旧冻结字节，输出新身份、变化理由与影响范围；不回填旧 hash 或复用失效审查 | 比较已接收版本和依赖，按自身规则重新创作/审查/批准；不得将旧输入确认或批准自动移植到新基线 |
| HC-08 | 生产端自检、消费者接收理解、最终产物验证是不同证据层 | 提供可离线检查设计包、确定性反例、真实模型评估及明确限制 | 提供实际接收、资源读取、派生和审查证据；最终 artifact 另以真实构建、运行及独立验收证明 |

**身份与状态细则。** 设计事实 ID、验收 ID、范围 ID、成员键和文件 hash 属于设计域；`ResourceIDs`、`SourceItemRefs`、`DoDItemRefs`、消费者 owner、批准及 Run 身份由 Workorch 自己的对象和流程决定。不得直接把设计 ID 填进这些字段，或为了生成有效请求伪造对象。设计事实的 `owner` 表示设计成员的唯一权威归属，不是消费者模块 owner 或执行权限。正式映射必须连接真实存在的双方对象，保留基线版本。来源于设计资源的抽取文本不能直接标为消费者的 `USER_EXPLICIT`；用户原始输入、用户确认决定与设计推导继续保留各自来源类别。

**来源通道与确认细则。** 按第 16.3 节，GoalText 与 AcceptanceRequirements 是消费者的直接输入通道；自动从设计抽取、已定稿设计验收和候选补充默认进入带来源的资源，不通过文字标签改变消费者分类。消费者用户明确采用某项为直接输入时，另记本次精确输入确认及设计来源；范围确认不替代该确认。没有直接验收时可用空列表，但所有设计必需项须在资源中完整承载，并待真实派生后逐项核对；不得将资源存在或完整 Goal 当作已证明逐项覆盖。

内部确认状态继续只有 `Fact.Status` 这一权威源：confirmed、proposed、unresolved。公开 `epistemicStatus` 是派生投影：confirmed/proposed 一一映射；unresolved 按关联问题显示 unresolved、assumed 或 conflicted，同一事实有假设和冲突时显示 conflicted 并保留全部问题。模态 MUST/MUST_NOT/MAY/NEEDS_CONFIRMATION 不等于批准；proposed MUST 不属于已确认强制要求。当前范围中影响合同的未确认规范选择和未知适用性阻塞交付；非规范、非必需且不影响当前合同的可选建议可保留可见。不得借过滤状态、降低模态或移除问题缩小范围分母。

**HC-04 固定预算。** 基线 Workorch 输入先对 `GoalText`、`TemplateID`、每条 `AcceptanceRequirements` 和每个 `ResourceRef` 做 TrimSpace；`WorkspaceID` 不在该函数中 trim。各文本须非空、有效 UTF-8、不含 NUL；要求列表结构上可空，但不能因此删除设计必需验收。限制为：

- `GoalText` ≤ 32,768 bytes；`AcceptanceRequirements` ≤ 128 条、每条 ≤ 4,096 bytes。
- `TemplateID`、`WorkspaceID` 各 ≤ 256 bytes；真实工作区身份由消费者提供。
- 有序 `ResourceRefs` ≤ 8 份，每项 ≤ 1,024 bytes，规范化后不得重复，不得静默排序或去重。
- `normalizedInputBytes = bytes(GoalText) + bytes(TemplateID) + bytes(WorkspaceID) + Σ bytes(AcceptanceRequirements[i]) + Σ bytes(ResourceRefs[i]) ≤ 131,072`。
- 上式不包含 JSON envelope、Version、Revision 或资源正文。单份资源正文为 UTF-8 且 ≤ 32,768 bytes；全部资源正文 `resourceSnapshotBytes = Σ bytes(actualResourceContent[i]) ≤ 131,072`，单独校验。
- 输入 `Version=1`、`Revision>0`；输入 hash 绑定 revision 和原有顺序。A→B→A 不能复用旧确认。尚无真实消费者上下文时，仅提供预览、预算和待绑定项，不能宣称真实请求校验已通过。
- 资源仅来自消费者认可的 `DeliverableDirectory` 范围，不接受任意远程 URL。BOM 和换行按真实文件字节计入；路径字符串检查不能替代 File owner 的实际读取和身份校验。
- 直接验收、真实模板 DoDItems、实际派生 AdditionalItems 的合并文本总量另受 131,072-byte 限制，各项 ≤ 4,096 bytes；AdditionalItems 最多 128 条，不杜撰全部候选总条数限制。模板/派生未知时仅报告已知下界及待验证状态，不能标为整体通过。
- 当前派生/提案/审查的请求组装另受 256 KiB 限制，以消费者实际 payload 和合同/提示为准；不能从输入/资源预算通过推出请求一定可发送。各层预算细则以第 16.2.1/16.2.2 节为准，模板或内容变化使相关结论失效。

**拟议逻辑字段组，不是现有接口。** HC-1 至少需要承载：①合同版本与固定设计身份；②完整公开包清单、publicPayloadHash/审查绑定、文件 hash 和公开投影/转换版本；③本次范围、明确排除项、全局约束与依赖闭包；④带来源和状态的规范事实、可判定验收、必要历史引用及 artifact 规范；⑤原始用户要求、消费者本次采用与候选补充的通道映射和分层确认；⑥有序资源计划、真实模板快照绑定、逐层预算与未知项；⑦生产端检查结果、未验证项和阻塞原因。其载体可以是现有 manifest 的扩展与有界文本资源，不预设新增通用导入器，也不要求建立平行事实库。

HC-1 不包含伪造的消费者正式 ID、批准、执行权限或成功证据；`artifact 规范` 只定义预期形态、运行方式与验收要求，不是已构建的最终 artifact。资料中出现的命令是待执行设计说明，不因交接而获得执行授权。

**联合验证完成线。** HC-01～HC-08 应分别保留生产端自检和消费端验证记录。真实消费者能读取指定字节、保持要求语义和范围、正确派生并完成对应审查，才可声明 HC 联合验证通过；只生成文件或通过本地 mock 不够。该联合验证不要求先完成 Workorch 所有运行时收口事项，也不证明最终 artifact 已通过。没有真实消费者环境或授权时，标记联合验证 NOT_RUN/BLOCKED，生产端符合其本地条件的实现仍可独立验收，但不得对外宣称跨项目闭环完成。

## 17 TF 11 API 与 Web 闭环

### 17.1 API 影响

当前应用入口为 `internal/modules/application/thoughtflow/service/document_sets.go`。相关 DTO 直接承载计划、运行、审查和导出信息；当前解码拒绝未知字段，因此必须同步更新客户端、服务端及契约测试，不能只改一端。

优先扩展现有文档集读写与审查响应。新增 handoff preview 等能力的路由、HTTP 方法、请求结构和错误码属于待设计接口，本文不将示意命名视为已存在端点。

响应至少能表达当前基线、质量状态、问题定位、影响摘要、公开包身份、预算明细和阻塞原因。任何修改请求都需携带或校验预期版本，冲突应提示重新读取，不允许悄悄覆盖用户刚更新的候选。

建议为业务错误提供稳定机器码，例如 `DESIGN_UNRESOLVED`、`REVIEW_STALE`、`HANDOFF_BUDGET_EXCEEDED`；名称为拟议。用户文案可以本地化，但机器码与验收语义需稳定。

### 17.2 最小用户路径

```text
查看成果集
  → 查看当前范围与必需内容
  → 点击缺口或冲突
  → 定位到事实和正文
  → 编辑建议或提交确认
  → 查看差异与受影响成员
  → 重新生成或审查
  → 定稿
  → 查看公开设计包或 Workorch 交接预览
```

每个阻塞项应让用户知道缺什么、影响什么、谁需要决定、如何处理，以及处理后需要重新检查什么。只显示“质量不通过”不足以支持收口。

### 17.3 必须保持的界面语义

- 当前工作候选、历史定稿和 Workorch 运行状态分开展示。
- 修改后立即将旧审查标为失效，不保留误导性的绿色通过提示。
- 固定版本阅读不被单篇 latest 覆盖。
- 用户确认与模型建议使用不同标识，不靠颜色单独传达差别。
- 交接预览显示范围、排除项、要求映射、资源顺序和字节预算。
- 超限、缺依赖和未确认等阻塞均有可操作解释，不提供绕过门禁按钮。
- 长关系表和问题列表支持定位与可读摘要，不要求用户理解内部对象结构。

主要落点为 `web/app.js`、`index.html`、`styles.css`、`web/i18n/keys.js`、`zh-CN.js`、`en-US.js` 及 `topicstore/document_set.go`。专题投影需回归 working/finalized 状态，不把单篇状态提升为成果集交付状态。

### 20.1 数据保护与发布顺序

1. 保存被授权范围内的原始数据备份，记录备份身份；备份不等于已验证可恢复。
2. 在临时工作区或被授权副本上验证新格式修订/定稿/备份恢复、历史引用、未知版本和损坏记录行为；旧格式只验证明确拒绝及原字节保留，不把兼容实现作为门禁。
3. 先引入显式工程用途和格式版本，再让新合同进入正式存储。
4. 先开放预览和检查，冻结公开载荷与审查绑定，再开放新格式定稿和 delivery。
5. Workorch 适配以独立启用开关或明确入口发布，避免影响普通导出。
6. 记录功能开启后的错误、阻塞、隐私和预算结果，再扩大适用范围。

功能开关不能成为绕过强制规则的开关。关闭新功能后若旧版本无法读取新数据，必须有明确的回退策略；不能仅回滚程序二进制就承诺数据可恢复。

### 20.2 回滚原则

回滚优先停用新增写入与交接，保留原始记录和失败证据。不得通过删除新字段、重写 hash 或丢弃未识别数据强行恢复旧程序可读。若选择迁移，需要验证反向能力或明确不可逆点，并在跨越前获得授权。

### 22.2 确定性回归程序

以下命令是仓库已定义的 Makefile 检查入口，状态统一为 `NOT_RUN`；本文没有执行它们。实施前先核对实际工作树的 AGENTS.md、Makefile、依赖和环境。DuckDB 等 CGO 链接环境需要按仓库约定准备，聚合测试优先使用 `make test`，不要以缺少链接参数的裸 `go test` 失败误判产品逻辑。

```bash
# 拟执行，NOT_RUN；在确认后的 thought-flow 仓库根目录执行
make fmt-check
make test
make build
make node-check
make node-test
# 聚合入口按当前 Makefile 选择，避免不必要的重复执行
make check
make ci-check
```

定向 Go 测试应覆盖 documentset、documentsetflow、documentsetstore、documentprofile、documentvalidation、documentflow、topicstore 及 application/thoughtflow/service，使用仓库要求的 CGO/链接环境。Web 应覆盖 `web/app.test.js`、`app.browser.test.js`、`api.e2e.test.js`，浏览器与实际模型 E2E 的环境和命令先核对脚本再执行。测试入口存在不等于所有环境已准备，也不授权收费调用；任何会调用模型或修改外部状态的测试需独立确认权限。

已有 E2E 的模型夹具可生成通用章节并固定返回审查通过，适合证明流程机制，不足以证明设计质量。必须另加有审定反例和真实模型输出的评估路径，不删除既有机制测试。

### 22.3 跨模型评估程序

1. 先冻结样例版本、模型精确标识、参数、提示词、预算、重试策略和及格线。
2. 明确每个模型拟支持的任务类型，不用某个简单样例推断全部工程能力。
3. 对每个模型和样例建立独立可追踪尝试，重复次数在运行前确定。
4. 使用同一设计基线、范围、全局约束及独立验收标准。
5. 分别执行首次生成、修订、错误反馈、重启恢复及模型切换场景。
6. 运行确定性规则并保留原始输出，语义评分依据冻结的 rubric。
7. 对冲突、遗漏、无依据确认、范围扩张和权限越界分别计数，不混成主观总分。
8. 比较可观察合同符合性；不同合理文字或实现不算失败。
9. 人工复核关键失败和抽样通过项，记录复核者角色及理由。
10. 输出适用范围、已知限制、未运行组合和是否允许进入相应生产任务。

当前生产重试拒绝 ModelHash 差异。跨模型评估必须新建独立尝试并关联同一评估样例，不能在同一运行记录中偷偷换模型，也不能放松生产身份校验来方便测试。

### 22.4 评估口径与门槛

建议分别统计需求召回、合同冲突、无依据推断、阻塞识别、范围遵从、恢复偏差、artifact 合同完整和消费者派生一致性。具体阈值在 D-08 决定并在运行前冻结；本文不虚构经过验证的数值。

关键安全或身份不变量出现一次违反，应单独判失败并分析，不被平均分稀释。纯格式差异与不影响合同的实现选择不应误判为不一致。禁止观察结果后降低阈值并宣称原计划通过。

### 22.5 执行记录最小字段

每次运行保存样例与合同 hash、模型/参数/提示词身份、尝试 ID、输入摘要与资源身份、开始结束时间、调用结果、重试原因、原始输出、规则结果、评分依据、人工复核、费用与失败类别。敏感输入的保存与公开应分层，不将评估日志直接附入 delivery。

测试状态需区分 NOT_RUN、BLOCKED、ERROR、FAIL、PASS；外部服务失败不能直接算设计质量失败或通过，应单独统计并按事先重试政策处理。

### 22.6 HC 联合消费者验证

消费者验证至少证明：正确读取目标与要求，按真实字段分类区分直接输入、设计抽取和候选补充；保留全局约束、不伪造来源 ID；在真实模板、派生结果及请求组装预算内提出与设计兼容的派生任务并接受相应审查；遗漏、超限或歧义时阻塞。按 HC-01～HC-08 及 AC-33/35 消费者层保存双方证据；资源入口真实接受文件是必要条件，但不足以证明正确理解。验证仅使用实际存在或已经另行实现的消费者入口，不因本文出现 HC-1 就假定通用导入器存在。

进一步验证最终 artifact 需要真实实施、构建和独立验收授权，不属于本次 Markdown 交付已完成事项。未执行此层时，报告应写“设计交接/理解已验证，最终 artifact 未验证”，不能合并成端到端成功。
