# 元数据向量策略

笔记索引和专题语义匹配统一使用 `models.EmbeddingText(Thought)`，输入接口不再接受正文。每篇笔记仍对应一个向量，不引入正文分块。此策略用于按主题发现笔记；摘要未覆盖的正文细节仍通过全文关键词检索查找。

## 输入与边界

- 标题优先使用用户标题，其次为提炼标题，最多 120 个 Unicode 字符。没有标题时不从正文或显示标题补入。
- 摘要最多 600 个 Unicode 字符。
- 标签先取用户标签，再取 AI 标签，忽略空值、大小写去重，合计最多 8 个，每个最多 24 个 Unicode 字符。
- 发出前压缩字段中的空白，安全裁剪超长手写或历史元数据；不会修改原始 Markdown。最坏输入为 912 个 Unicode 字符加字段名与分隔符，UTF-8 字节数小于 4096。字符、字节和模型 token 是不同单位；不把字符上限声称为精确 token 数。
- 没有任何可用元数据时跳过该笔记的向量，仍保存全文关键词索引。

## 摘要与标签生成

大模型提炼仍读取完整有效正文：普通笔记使用当前编辑正文，URL 笔记使用抓取正文并保留用户旁注。新的 `assets/prompts/refine_system.md` 要求摘要覆盖主题、目的、关键实体和技术术语、结论与范围约束，保留否定、不确定性及“提案/事实”区别；标签围绕实际讨论内容，通常 3–6 个，不强凑数量，不虚构事实，不输出凭据。

服务端拒绝空摘要、超长摘要或标题、过多或超长标签，以及 URL、多行或重复标签等不合格输出。模型适配器先规范化、去重标签再验证，服务端也验证其他 provider 的结果。不静默截断新生成摘要；后台提炼最多尝试 3 次，失败保留上一次成功的元数据并记录失败任务。正文修改事件会重新提炼，元数据完成后再更新向量；标题和用户标签修改直接影响索引，不触发不必要的提炼。

本地无 Key 模式继续使用规则提炼，摘要为有效正文的有界摘录，标签改为完整英文词匹配，避免 `plain` 误中 `ai`、`ongoing` 误中 `go`。它无法达到模型摘要的覆盖质量。提示词和结构校验也不能自动证明大模型输出事实正确，用户仍需审阅关键笔记。

正文编辑后提炼为异步过程，完成前语义检索仍基于上一次成功的元数据。提炼失败会保留该状态，修复失败原因后可重试提炼。

## 缓存与部署

向量缓存按规范化元数据哈希识别。新格式包含字段名，因此原全文向量在重建时失效并重新计算。仅正文变化但元数据未变化时可复用向量；标题、摘要或参与计算的标签变化后重新计算。关键词索引始终更新全文，专题硬性关键词规则也继续检查全文。

工作区重建仍先计算全部向量，再以事务替换文本与向量，失败保留旧索引。更新二进制并重启服务后，启动恢复会自动重建索引；也可通过 `POST /api/system/reindex` 重建。重建不会批量重写现有笔记的摘要或标签；需要应用新生成约束的旧笔记，可单独重试提炼。

## 回归覆盖

- 模型层：只取元数据、标题优先级、标签去重、超长四字节 Unicode 输入边界。
- AI 层：提炼请求保留完整长正文，摘要和标签硬约束、空摘要及超限输出拒绝，本地 UTF-8 与误标签。
- Refiner：无效摘要重试且不覆盖上次成功摘要；真实正文 PATCH 事件触发元数据刷新。
- Search：通过真实 HTTP 适配器证明超长正文不进入 embedding 请求；旧全文缓存失效、重建恢复 ready、元数据缓存复用、摘要变化重算、全文关键词仍可检索。
- SearchDB：正文单独修改保留元数据向量，元数据变化原子失效旧向量。
