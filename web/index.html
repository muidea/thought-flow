      Custom document formats

      Define a DocumentProfile

      Customize a document format by defining its purpose, matching conditions, input parameters, section structure, template, and archive rules.

      Custom profile directory
      document-formats/
      Active profiles
      Loading profiles
      Purpose and definition scope

      Define a custom DocumentProfile when the built-in formats do not cover the required document structure or archive rules. A Profile should describe the document type and purpose, when it applies, which parameters it accepts, how its sections are organized, how the final Markdown is rendered, and which conditions a valid result must satisfy.

      DocumentProfile
      The complete definition of a custom document format, including identity, applicability, parameters, sections, template, and archive rules.
      DocumentFormat
      The Markdown source file used to define and version a custom DocumentProfile.
      Draft and published
      Drafts are editable and inactive. Published ID/version files are automatically loaded, active, and immutable.

      What to define first

      Before writing the Format file, make the target document requirements explicit.

      • Purpose and applicability: what document is being defined, what it is used for, and when this Profile should or should not match.
      • Parameters and sections: which values are configurable, which sections are required or optional, and how sections should be ordered.
      • Archive rules: required content, body length, references, allowed sections, and other conditions that determine whether the document is valid.

      A DocumentProfile should define a verifiable document format, not only a writing tone or a set of general instructions.

      From document contract to active profile
      1. Define the document purpose, applicability, and stable profile ID.
      2. List configurable inputs and required or optional sections.
      3. Define matching examples, the Markdown template, and archive rules.
      4. Create the complete Format file under drafts, then place it under published/<profile-id>/vN.md when it is ready to take effect.
      5. ThoughtFlow detects the file automatically; valid profiles become active, while invalid files are isolated and reported.
      <configured-profile-dir>/
├── drafts/
│   └── team-rfc.md
└── published/
    └── custom.team-rfc/
        ├── v1.md
        └── v2.md
      DocumentFormat example

      YAML front matter defines identity, matching, inputs, generation guidance, and validation. The Markdown body defines the deterministic final layout. Custom IDs must not use the builtin namespace.

      ---
id: custom.team-rfc
version: 1
name: Team RFC
family: design
description: Design contract for team-owned system changes
enabled: true
auto_match:
  enabled: true
  priority: 50
  use_when:
    - The requested document is a team RFC
  positive_examples:
    - Create a team RFC for the proposed change
  negative_examples:
    - Create an informal implementation note
inputs:
  - key: audience
    label: Audience
    required: false
    default: Engineering reviewers
validation:
  allow_unknown_sections: false
  require_non_empty_sections: true
  minimum_body_chars: 500
  maximum_body_chars: 12000
  heading_level: 2
generation:
  additional_instructions: |
    Cover failure paths, compatibility, testing, and rollback.
---
# {{title}}

> {{summary}}

## Context

{{section:context|required}}

## Proposal

{{section:proposal|required}}

## Testing and rollback

{{section:verification|required}}

## References

{{references}}
      Template DSL and constraints

      The restricted template organizes the final Markdown with deterministic placeholders. Formats cannot execute code, access files, call the network, or change archive behavior.

      {{title}} {{summary}} {{parameter:key}} {{section:key|required}} {{section:key|optional}} {{references}}
      • Use a stable family: note, research, design, article, record, or other.
      • Every required section must appear exactly once and receive non-empty generated content.
      • Published versions are immutable; changes require a higher version.
      • Use precise positive and negative examples so ordinary discussion does not trigger a specialized profile.
      Activation, updates, and troubleshooting

      The configured directory is the complete product interface for custom profiles. Files under drafts remain inactive; complete Markdown files under published are scanned and loaded automatically.

      <configured-profile-dir>/published/
└── custom.team-rfc/
    ├── v1.md
    └── v2.md
      • Only Markdown files inside published participate in matching and generation; drafts are never active.
      • Start a new custom profile at version 1. Any contract change must use a higher version instead of overwriting an existing file.
      • If a profile is not active, check the loaded profile list and issue count, then inspect enabled, auto_match, examples, ID, version, and template fields.
      • A malformed or conflicting file is isolated without affecting built-in profiles or other valid custom profiles.
